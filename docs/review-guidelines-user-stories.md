# 用户故事 Review 规范

> 本文档定义用户故事的 review 维度、流程和检查清单。
> 适用于 `docs/domain/user-stories-*.md` 中的所有用户故事。
> 文档层级：L2 规范层（修改需 PR + 变更记录）。

---

## 1. Review 时机

| 时机 | 触发条件 | 产出 |
|------|---------|------|
| **新建 review** | 新模块用户故事首次写完 | review 记录（通过/待修改） |
| **变更 review** | 已有故事修改（加字段/改状态机/改验收标准） | 影响分析 + review 记录 |
| **跨模块 review** | 多个模块故事都写完后，检查模块间一致性 | 一致性报告 |
| **开发前 review** | 某个故事即将进入 TDD 开发前 | 最终确认（开发后不再改需求） |

## 2. 五个 Review 维度

### 2.1 完整性（Completeness）

> 故事是否覆盖了所有该覆盖的场景？

**检查清单**：

- [ ] 正常路径（happy path）是否清晰描述？
- [ ] 异常路径是否列举？（网络断开、数据不存在、权限不足、并发冲突）
- [ ] 边界条件是否考虑？（空值、最大值、零数量、过期边界日）
- [ ] 所有相关角色是否都有对应操作？
- [ ] 是否有"谁触发"和"谁接收结果"？
- [ ] 是否说明了与其他模块的交互？（如：入库完成后通知库存模块）
- [ ] 是否覆盖了数据的完整生命周期？（创建→使用→归档/删除）
- [ ] 批量场景是否考虑？（批量导入、批量操作）
- [ ] 离线场景是否考虑？（PDA 断网）
- [ ] 打印/导出需求是否明确？

**常见缺陷**：
- 只写了"创建"没写"修改/停用/删除"
- 只写了正常流程没写异常处理
- 缺少"谁能看到这个数据"（权限/多租户）

### 2.2 一致性（Consistency）

> 故事之间、故事与已有文档之间是否矛盾？

**检查清单**：

- [ ] 同一实体在不同故事中的字段是否一致？（如"商品"在 M1/M2/M3/M4 中的属性）
- [ ] 状态名称是否全局统一？（不能 M2 叫"已完成"、M4 叫"完成"）
- [ ] 角色名称是否与角色清单一致？
- [ ] 术语是否统一？（不能一处叫"ASN 收货单"另一处叫"ASN"缩写混用）
- [ ] 验收标准的编号是否与其他故事冲突？
- [ ] 跨故事约束是否与 governance.md / ADR 一致？
- [ ] 状态机的终态是否与其他模块的起始态衔接？（如 M2 "已完成" → M3 库存增加）
- [ ] API 接口约定是否与 coding-standards.md 一致？（URL 命名、错误码格式）

**常见缺陷**：
- M2 说"ASN 是单品"但某处验收标准暗示多品
- 不同模块对"审批"的描述不一致（有的说"主管审批"有的说"企业微信审批"）
- 状态机之间的衔接断裂（M2 上架完成后 M3 库存怎么增加没说清）

### 2.3 可验证性（Testability）

> 验收标准是否能直接转化为测试用例？

**检查清单**：

- [ ] 每条验收标准是否有明确的"给定→当→那么"（Given-When-Then）？
- [ ] 是否有模糊词？（"快速"、"合理"、"适当"、"尽量" ← 全部不合格）
- [ ] 数值是否具体？（"预警天数可配置" ✓ vs "提前预警" ✗）
- [ ] 是否能写出对应的 L3 业务流程测试？
- [ ] 是否能写出对应的 L4 错误路径测试？
- [ ] 是否能写出对应的 L8 权限测试？（"仓库主管可操作" → 测试其他角色不可操作）
- [ ] 是否能写出对应的 L11 幂等性测试？（写操作重复提交结果一致）

**常见缺陷**：
- "系统应该响应迅速" ← 不可测
- "支持大量数据" ← 多大？1 万？100 万？
- "用户体验良好" ← 无法自动化验证

### 2.4 可实现性（Feasibility）

> 技术上能否在当前架构和资源下实现？

**检查清单**：

- [ ] 是否依赖尚未就绪的外部系统？（如药监局接口资质未申请）
- [ ] 是否依赖尚未采购的硬件？（如温湿度探头、蓝牙打印机）
- [ ] 是否超出当前技术栈能力？（如需要实时视频流但只有 REST API）
- [ ] 性能要求是否在架构承受范围内？
- [ ] 离线同步的冲突解决策略是否明确？
- [ ] 与外部系统的接口协议是否已确认？（API 文档是否可获取）
- [ ] 是否有法律/合规前置条件？（如资质申请、数据跨境）

**常见缺陷**：
- 写了"对接码上放心"但没确认 API 是否开放
- 写了"自动识别追溯码"但没确认码的格式标准
- 写了"企业微信审批"但没确认企业微信 API 权限是否已开通

### 2.5 GSP 合规性（Compliance）

> 是否满足 GSP 法规对该环节的要求？

**检查清单**：

- [ ] 是否有双人验收/复核要求？（GSP 规定的环节必须有）
- [ ] 是否有审计追踪？（所有库存变动、审批、关键操作）
- [ ] 是否有不可篡改性？（审计记录 append-only）
- [ ] 是否有批次追溯？（从入库到出库到客户的完整链路）
- [ ] 是否有效期管理？（近效期预警、过期锁定）
- [ ] 是否有温湿度记录？（冷链环节）
- [ ] 是否有资质校验？（供应商/客户/门店的经营范围）
- [ ] 是否能生成法定台账？（验收记录、养护记录、出库复核记录等）
- [ ] 是否有色标管理？（合格/隔离/不合格分区存放）
- [ ] 是否有不合格品处置流程？（隔离→审批→报损/退货/销毁）
- [ ] 数据保存期限是否满足法规要求？（通常 ≥ 5 年）

**常见缺陷**：
- 缺少双人验收（GSP 强制）
- 审计追踪只记了"谁做了什么"没记"旧值是什么"
- 没有色标区域管理（合格品和不合格品混放）
- 缺少养护记录

## 3. Review 流程

```
故事编写完成
    ↓
自审（作者按 5 维度 checklist 逐条过）
    ↓
标注 review 结论：
  - PASS：5 维度全部通过
  - NEEDS_WORK：标注哪些维度有问题 + 具体问题
    ↓
修改（如有）
    ↓
最终确认（PASS）
    ↓
可进入 TDD 开发
```

### 自审 vs 他审

| 阶段 | 方式 | 说明 |
|------|------|------|
| Wave 0-2（个人） | 自审 | 按 checklist 逐条过，诚实标注 |
| Wave 3+（如有团队） | 他审 | 另一人按 checklist review，留评论 |

### Review 记录格式

在用户故事文件末尾追加：

```markdown
---

## Review 记录

| 日期 | 版本 | 审查人 | 结论 | 备注 |
|------|------|--------|------|------|
| 2026-05-15 | v1 | 自审 | NEEDS_WORK | 一致性：M2/M3 状态衔接未明确 |
| 2026-05-16 | v2 | 自审 | PASS | 已补充状态衔接说明 |
```

## 4. 常见缺陷模式（从 wms 已有故事提炼）

| # | 模式 | 示例 | 修复方式 |
|---|------|------|---------|
| 1 | **状态衔接断裂** | M2 上架完成后 M3 库存怎么增加？谁触发？ | 在跨故事约束中显式写明"上架完成 → 发出 domain event → M3 消费" |
| 2 | **配置项散落** | "可配置"出现 10+ 次但没有统一的配置项清单 | 每个模块末尾汇总该模块的系统参数清单 |
| 3 | **角色模糊** | "仓库主管（或外部系统通过 API）" ← 两种触发方式混在一个故事里 | 拆成两个验收标准分别描述 |
| 4 | **审计遗漏** | 某个操作没写"写入审计追踪" | 跨故事约束兜底 + review 时逐条检查 |
| 5 | **幂等性遗漏** | 写操作没说明重复提交的行为 | 跨故事约束统一要求 + review 时检查 |
| 6 | **离线冲突未说明** | "PDA 离线支持"但没说冲突怎么解决 | 补充冲突策略（如：离线期间同一库位被占用怎么办） |
| 7 | **外部依赖未标注** | 依赖企业微信 API / 追溯码平台 API 但没标注 | 在故事头部"依赖"段显式列出外部系统 |

## 5. 与治理体系的集成

### 5.1 自动化 vs 人工（明确分界）

| 检查项 | 方式 | 脚本/人工 | 维度 |
|--------|------|-----------|------|
| 每个故事有 `### 验收标准` 段 | 正则匹配 | 🤖 脚本 `check_user_story_structure.py` | 完整性 |
| 验收标准是编号列表 | 正则匹配 | 🤖 脚本 | 可验证性 |
| 无模糊词（黑名单） | 关键词扫描 | 🤖 脚本 | 可验证性 |
| 写操作故事提到"审计追踪" | 关键词 | 🤖 脚本 | GSP |
| 写操作故事提到"幂等" | 关键词 + 文件级跨约束兜底识别 | 🤖 脚本（warn） | 完整性 |
| 有"跨故事约束"段 | 结构匹配 | 🤖 脚本 | 完整性 |
| 故事编号连续无重复 | 正则 + 排序 | 🤖 脚本 | 一致性 |
| 角色名在白名单内 | 关键词匹配（剥离括号附注）| 🤖 脚本（warn） | 一致性 |
| 状态变更声明审批源 | 触发关键词 + 必含字段 | 🤖 脚本 `check_approval_source_chain.py` | GSP / 一致性 |
| 配置项在 M1-008 配置中心列出 | 关键词比对 | 🤖 脚本 `check_config_center_consistency.py` | 一致性 |
| 附录跨模块引用 | 关键词比对 | 🤖 脚本 `check_doc_links.py`（增强）| 一致性 |
| **PDA 操作故事三件套**（字段表 + 扫码顺序 + 离线声明）| 表格识别 + 扫码模式 + 关键词 | 🤖 脚本 `check_pda_story_completeness.py` | 完整性 / 可验证性 |
| 异常路径是否完整 | 业务理解 | 👤 人工 | 完整性 |
| 状态机之间是否衔接 | 跨文档语义 | 👤 人工 | 一致性 |
| 字段在不同故事中是否一致 | 跨文档语义 | 👤 人工 | 一致性 |
| 术语是否统一 | 语义判断 | 👤 人工（未来可半自动：术语表） | 一致性 |
| 验收标准是否真的可测试 | 语义判断 | 👤 人工 | 可验证性 |
| 数值是否具体（有默认值） | 语义判断 | 👤 人工 | 可验证性 |
| 离线冲突策略是否说明 | 业务理解 | 👤 人工 | 完整性 |
| GSP 法规是否合规 | 法规知识 | 👤 人工 | GSP |
| 业务逻辑是否矛盾 | 领域理解 | 👤 人工 | 一致性 |
| 外部依赖是否可行 | 外部确认 | 👤 人工 | 可实现性 |
| 跨模块数据流是否完整 | 架构理解 | 👤 人工 | 完整性 |
| 配置项是否有默认值 | 语义判断 | 👤 人工 | 可验证性 |

> **原则**：脚本负责"格式对不对"，人工负责"内容对不对"。
> 脚本通过 ≠ 故事合格；脚本不通过 = 故事一定不合格。

### 5.2 脚本使用

```bash
# 跑用户故事结构检查
python3 scripts/governance/check_user_story_structure.py

# JSON 输出
python3 scripts/governance/check_user_story_structure.py --json

# 也可通过 just
just gov-t1  # T1 全套包含此脚本
```

### 5.3 Review 与 TDD 的关系

```
用户故事 PASS
    ↓
从验收标准推导 L3 业务流程测试（外层红）
    ↓
从验收标准推导 L4 错误路径测试
    ↓
从"角色可操作"推导 L8 权限测试
    ↓
从"写操作"推导 L11 幂等性测试
    ↓
进入 TDD 红绿循环
```

**验收标准 = 测试用例的需求来源**。如果验收标准写得不可测，TDD 就无法启动。

## 6. PDA 操作类故事的"三件套"标准

> 适用于保管员/收货员/养护员等用户在 PDA 上的核心物理操作故事。
> 由 `check_pda_story_completeness.py` 自动检查，不达标即 T1 失败。

### 6.1 三件套定义

| # | 件 | 内容要求 | 自动识别启发 |
|---|----|---------|-------------|
| 1 | **字段表** | Markdown 表格，列出该 PDA 操作要录/扫的所有字段（必填/可选/系统带出/扫码录入）| 表头含 `字段` / `项目` / `必填` / `核对项` 任一关键词 |
| 2 | **扫码顺序** | 明确的步骤序列（先扫什么再扫什么），通常用代码块 + 箭头 `→` 或编号列表 | 文本中出现 `扫 X → 扫 Y` 模式 或 ≥2 处扫码动作 |
| 3 | **离线声明** | 故事正文显式说明断网时的行为；冲突走跨故事约束兜底（不静默覆盖）| 含 `离线` 或 `断网` 关键词 |

### 6.2 适用范围（白名单）

`check_pda_story_completeness.py` 内 `REQUIRED_PDA_STORIES` 集合维护所有需检查的核心 PDA 故事 ID。新增 PDA 操作故事时，应将故事 ID 加入该集合（让脚本守护）。

### 6.3 例外（豁免）

`EXEMPT_STORY_IDS` 集合维护**含"PDA"但不算操作类**的故事（如看板/查询/配置类）。这类故事不强制三件套。

### 6.4 与开发的对应

| 三件套 | 直接服务 |
|-------|---------|
| 字段表 | PDA 表单设计、API 字段契约（utoipa → OpenAPI）、领域实体属性 |
| 扫码顺序 | PDA 交互测试用例（L3）、状态机测试（L1）|
| 离线声明 | PDA SDK 设计（H6 状态机引擎、SQLite 暂存）、契约一致性测试；首个正式版本后再启用 L9 |

> 推论：PDA 故事三件套不齐 = TDD 无法启动（开发要猜）= 故事不合格

## 7. 用户故事验收执行模板

### 7.1 定位与适用范围

Review 记录回答“需求是否可进入开发”，验收记录回答“实现是否已被证据证明”。验收记录
不替代故事验收标准、质量矩阵、测试报告或 S4 外部证据，只负责把每条 AC 映射到可运行
检查和证据。

- 新故事和本次被修改的故事，在声明完成前必须填写验收记录。
- 既有故事不批量回填，后续修改或推进时逐步补齐。
- 验收层级由 `governance/quality-matrix.toml` 的故事类型推导，不得手工降低。
- 不复制质量矩阵十二维度；验收记录只引用矩阵状态和聚合检查结果。

### 7.2 结论语义

| 结论 | 判定 | 质量矩阵状态 |
|---|---|---|
| `PASS` | 每条 AC 都有有效证据，适用测试和 S4 条件全部满足，无未关闭缺口 | 可进入 `[[stories]]` |
| `NEEDS_WORK` | 任一 AC 缺实现、测试、截图或真实环境证据，或仍有恢复条件 | 保持 `[[deferred_stories]]` |

局部测试、页面截图、Mock 或容器联调只能证明对应切片；只要故事要求的真实设备、硬件、
外部系统或发布证据未满足，故事整体仍为 `NEEDS_WORK`。

### 7.2.1 验证证据分层

`V0-V4` 只回答“证据来自哪里”；验收深度仍由 `S1-S4` 决定，测试内容仍由 `L1-L11`
决定，执行时机仍由 `T1-T4` 决定。四套编号不得互相替代。

| 证据层 | 证明什么 | 最低证据 |
|---|---|---|
| V0 静态接线 | 需求、字段、菜单、权限、路由、OpenAPI、矩阵和文档已对齐 | diff、self-check、治理检查或人工映射 |
| V1 自动化行为 | 正常、异常、权限、幂等等行为可重复验证 | 单元、契约、集成测试；Mock 只计入本层 |
| V2 真实数据 | 生产代码路径确实读写真实测试数据库 | 隔离测试库、迁移、确定性种子、API 查询/回读结果 |
| V3 真实用户链路 | 用户能经真实登录、菜单和页面完成流程 | 关闭 dev-mock 的 Playwright、报告和适用截图 |
| V4 条件环境 | 外部系统、PDA、硬件或发布条件在目标环境成立 | dev/staging 回执、真机/硬件、性能或灰度发布证据 |

最低适用规则：所有故事覆盖 V0/V1；使用数据库的 API 或查询覆盖 V2；有正式页面覆盖
V3；故事类型要求外部系统、PDA、硬件或发布证据时覆盖 V4。不适用层必须写明原因。

V2 不允许只证明“请求 200、结果为空”。查询故事至少准备一条可追踪的确定性测试数据，
记录业务键和预期状态，并断言 API 或页面返回该业务键与正确数量；写入故事必须从真实
数据库回读。测试数据只能进入隔离测试库或明确的开发库，不复制生产数据，不提交真实
凭据。V3 应复用 V2 的业务键，使截图和浏览器断言能追溯到同一行数据。

### 7.3 可复制模板

```markdown
## 验收记录

- 故事：`US-<模块>-<编号>`
- 验收基线：`<commit / PR / tag>`
- 验收层级：`S1 / S2 / S3 / S4`（由质量矩阵推导）
- 质量矩阵状态：`stories / deferred_stories`
- 证据层覆盖：`V0 / V1 / V2 / V3 / V4`（不适用写明原因）
- 验收日期：`YYYY-MM-DD`
- 整体结论：`PASS / NEEDS_WORK`
```

### 7.3.1 管理端菜单页补充验收项

适用于新增或修改管理端菜单页。开发 API mock、自检或直接访问页面只能作为辅助证据，不能替代真实菜单链路。

| 项 | 最低验证要求 | 必须留下的证据 |
|---|---|---|
| 发布版本一致性 | 执行迁移后，调用 `GET /api/v1/admin/menus/published`，确认返回的 `version_no` 是数据库最新已发布版本，且包含页面 `view_id` / `path` 与 `permission_key` | 迁移执行记录 + 菜单 API 响应或等价查询结果 |
| 权限可见性 | 用目标角色验证菜单出现；对无权限角色验证菜单隐藏，直接访问时返回 403 或受控拒绝（适用时） | 角色、权限码、正/反向 API 或浏览器结果 |
| 真实页面可见 | `WMS_WEB_ADMIN_DEV_MOCK=0` 下用真实 Playwright 展开父级菜单、点击新增菜单、断言页面唯一标题/标识可见 | 页面级 PNG、Playwright 报告与 spec 路径 |
| 刷新后保持 | 迁移或发布后新建浏览器上下文/重新登录，确认菜单仍可见，避免只验证旧缓存 | 新会话 E2E 结果或截图 |

菜单页验收记录至少增加一行 `MENU-VISIBILITY`，并在整体结论中说明真实菜单 API、权限和页面截图是否全部通过；仅 dev-mock 通过时保持 `NEEDS_WORK`。

### 7.3.2 正式前端页面补充验收项

适用于新增或修改 Web/PDA 正式页面。原始字段名和状态码可以保留在 API 契约中，但不能直接替代面向用户的业务文案。

| 项 | 最低验证要求 | 必须留下的证据 |
|---|---|---|
| 中文业务文案 | 字段标签、表头、按钮、弹窗标题、状态、选项、错误和空状态默认使用中文；协议缩写、物理表名、编码和 ID 可保留，但需有中文语义，禁止只显示 `snake_case` 原始字段名 | Playwright 中文定位断言 + 页面截图；抽查查询区、列表和详情 |
| 控件语义 | 互斥单值使用单选控件；可组合的“或”条件使用多选；布尔值使用复选框/开关；存在受控字典时不得退化为自由文本 | 故事页面契约或 AC 明确控件类型与选择语义 |
| 契约一致 | 控件值必须按 OpenAPI/API 契约传递；多选不得只取第一项或仅在前端合并分页结果 | 请求参数断言 + API/领域测试 |
| 交互结果 | 多选至少同时选择两个值，断言请求包含两值且结果符合并集语义；单选断言不可同时选择多个值 | 真实 Playwright 报告和适用截图 |

正式前端页面的验收记录至少增加一行 `UI-SEMANTICS`。任一用户可见业务字段仍以原始英文键作为唯一标签，或控件类型与查询语义/API 契约不一致时，整体结论保持 `NEEDS_WORK`。

### 7.3.3 查询 / 探查类页面业务内容补充验收项

适用于正式的列表查询、外部接口探查和运行排障页面。控制字段只能证明“查到一行”，不能证明用户看到了实际业务内容。

| 项 | 最低验证要求 | 必须留下的证据 |
|---|---|---|
| 列表业务可识别 | 至少展示业务键和能识别对象的核心业务摘要；只有 ID、状态、时间、重试次数等控制字段不得通过 | V2 确定性业务键、非空核心字段的 API 断言；V3 同字段页面断言和截图 |
| 详情内容完整 | 按故事字段契约展示安全白名单内的实际业务内容，并按业务信息、处理信息等分区使用中文标签 | 详情 API 字段断言、Playwright 中文字段和值断言、详情截图 |
| 嵌套内容结构化 | 明细行、包装层级等集合使用表格或列表；不得把 JSON 字符串作为唯一用户界面 | 至少一组真实嵌套测试数据、结构化控件断言和截图 |
| 安全边界 | 原始报文、密钥或受限字段不得为满足“内容可见”而直接开放；结构化业务内容需有服务端字段白名单及大小/条数上限；使用脱敏摘要或另立权限故事 | API 不返回原始字段的反向测试、超限测试、页面敏感字段否定断言 |
| 数据可追踪 | V3 必须复用 V2 的业务键和预期值，禁止以“请求 200、列表非空”代替内容验收 | 种子业务键、预期字段值、API/页面/截图三者映射 |

查询 / 探查类页面的验收记录至少增加一行 `BUSINESS-CONTENT`。任一页面只能看到状态和技术控制列、详情只有未解释的 JSON，或 V2/V3 未复用同一业务键时，整体结论保持 `NEEDS_WORK`。

### 7.3.4 外部连接探测补充验收项

适用于 REST、数据库、消息系统等外部连接的“测试连接”功能。字段校验、关闭端口或用常量
断言同一常量，只能证明失败分支可执行，不能证明真实认证、结构和最小权限契约。

| 项 | 最低验证要求 | 必须留下的证据 |
|---|---|---|
| 正反向认证 | 使用真实协议证明正确凭据成功、错误凭据失败；Mock 的未认证写请求还要断言没有业务副作用 | 隔离容器或目标环境的正反向结果、Mock 状态前后对比 |
| 结构与最小权限 | 真实账号覆盖正确结构/最小权限成功，以及缺对象、缺字段、少权限、权限过大失败；禁止用生产数据做探测写入 | 临时账号与受控 DDL、各场景退出码或测试报告、清理结果 |
| Secret 传递 | 明文 secret 不进入命令行参数、URL、日志、错误、审计或截图；命令行工具通过 stdin、文件描述符或等价安全通道接收 | argv 否定测试、错误脱敏测试、CR/LF 注入反向测试 |
| 目标约束 | 携带凭据的探测只允许命中部署白名单内的受信端点；默认拒绝 userinfo、未授权主机及私网/回环绕过 | 白名单正向测试、主机/IP 变体与 userinfo 反向测试 |
| 证据分层 | 本地 Mock 只计 V1，隔离真实数据库/协议计 V2；除非故事明确允许“软件路径关闭”，容器证据不得替代目标环境 V4 | 验收记录明确写出证据层、适用范围和未完成的外部条件 |

外部连接故事的验收记录至少增加一行 `CONNECTION-PROBE`。只有字段检查、关闭端口、常量
自证或未认证 Mock 正常路径时，整体结论保持 `NEEDS_WORK`。
