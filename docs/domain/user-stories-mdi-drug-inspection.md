# 用户故事：M-DI 药检单

> 模块：M-DI drug-inspection
> 性质：WMS 负责入库资料写入；药检单独立审核，独立客户平台负责只读查询
> 首期：PC Web + 后端闭环；不包含 PDA
> 依赖：M1 商品/客户地址、M2 入库、M3 库存、M4 出库、M-QL 质量联系单、
> M-VR 规则、H1 权限、H2 审计与事件、H-FILE 文件存储
> 关联 ADR：[ADR-0042](../adr/0042-drug-inspection-customer-portal.md)

---

## 范围与优先级

1. 第一阶段以 WMS 人工上传药检单为正式入口；已实现的上游药检平台配置保留为可选能力，
   不阻塞人工闭环。
2. WMS 是药检单、审核结论和版本关系的唯一写入事实源。
3. 客户查询使用独立部署的客户平台和独立 PostgreSQL 只读模型，不读取 WMS 数据库，
   不在客户请求链路调用 WMS API。
4. 一个 ASN 只有一个商品，但可以包含多个批号；每个批号分别关联药检单。
5. 上游随货同行单是供应商随采购入库货物提供的资料，与 H9 出库随货同行单分离。

## US-DI-001：WMS 入库资料录入与药检单复用

**作为** 收货员（资料录入人）
**我要** 在独立入库资料页面查询 ASN 的资料完成情况，并录入药检单和上游随货同行单
**以便** 每个实际到货 ASN 的批号药检单和供应商随货资料都可追溯

### 药检单字段表

| 字段 | 必填 | 来源 | 说明 |
|------|------|------|------|
| 货主 `owner_id` | 是 | 当前上下文 | 所有查询和写入按货主隔离 |
| ASN `asn_id` | 是 | 当前入库单 | 一个 ASN 只能有一个商品 |
| 商品 `product_id` | 是 | ASN | 使用稳定商品 ID，不以名称匹配 |
| 批号 `batch_no` | 是 | ASN 批号行 | 同一 ASN 可有多个批号 |
| 报告编号 | 是 | 上传人录入/上游带出 | 用于客户展示和审计 |
| 权威原件 `original_file_id` | 条件必填 | H-FILE | 已复用时引用现有药检单版本 |
| 来源 | 是 | 系统 | 人工上传、上游平台、已有报告复用 |
| 图像处理方式 | 图片必填 | 上传人选择 | 不处理、原色增强、黑白增强 |
| 上传人 `uploaded_by` | 是 | 当前用户 | 后续不得作为同一记录审核人 |
| 创建时间 | 是 | 系统 | 进入审计时间线 |

### 验收标准

1. ASN 创建和维护继续遵守“一 ASN 一商品”；ASN 可以建立多个批号行。
2. 每个批号处理前，系统按 `owner_id + product_id + batch_no` 查找当前有效的已确认药检单。
3. 找到当前有效版本时，上传人可以直接关联复用，不重复上传文件；复用关系仍记录 ASN、
   操作人、时间和来源版本。
4. 没有可复用报告时，上传人通过 H-FILE 上传权威原件：
   - JPG/PNG 单文件不超过 5MB；
   - JPG/PNG 解码后不超过 5000 万像素，任一边不超过 12000 像素；
   - PDF 沿用 H-FILE 50MB 上传上限；
   - 文件类型只允许 `image/jpeg`、`image/png`、`application/pdf`。
5. 图片上传完成后、提交审核前，由上传人手工选择：
   - `none`：不做图像增强；
   - `color_enhance`：保留原色并轻度去噪；
   - `black_white_enhance`：自适应二值化并轻度去噪。
6. 系统先修正图片方向，再生成处理预览；原图与处理后副本并排展示。上传人可以重新选择
   处理方式，但不得覆盖权威原件。
7. 第一阶段以人工上传为正式入口。现有药检平台配置继续支持多平台、凭证引用、超时和状态，
   但真实自动获取与联调不作为人工闭环前置条件。
8. 草稿和待确认记录可以修改，所有上传、修改、处理选择、复用和提交动作写入 H2 审计。
9. 权威原件不可删除或覆盖，按 H-FILE 的 GSP 附件策略保留至少 5 年。
10. 写操作支持 `Idempotency-Key`；重复上传确认或重复关联不产生重复业务记录。
11. 前端验收必须连接真实 WMS API、H-FILE 实现和 PostgreSQL 测试库，使用真实创建的 ASN、
    批号和附件完成上传、复用、修改及刷新后回读；禁止用 Vite dev mock、Playwright 路由拦截
    或页面内存状态替代。E2E 必须保存上传成功、复用成功和版本记录三类页面截图。

### 入库资料清单与上游随货同行单验收标准

1. WMS 管理端在“入库业务 / 入库资料”下提供“入库资料录入”菜单，页面类型为列表型；每个 ASN 一行，
   同时显示上游采购订单号、货主、供应商、商品、实际收货时间和批号摘要。
2. 查询日期口径为实际收货时间，默认最近90天并允许人工调整。未实际收货的 ASN 清空日期后
   可以查询，药检单状态显示“待收货/待批号”，不计入药检单缺失。
3. 列表分别显示药检单和上游随货同行单状态。药检单按实际批号显示待收货/待批号、未录入、
   部分录入、已齐全；上游随货同行单只显示未上传、已上传。
4. 公共 QueryPanel 提供通用胶囊快捷标签。本页配置“药检单不齐”和“上游随货同行单不齐”；
   点击标签立即查询，两个标签同时启用时按任一资料不齐（OR）匹配。
5. 每行使用一个“录入资料”入口，弹窗内分药检单和上游随货同行单两个页签；药检单继续遵守
   本故事前述按批号复用、上传和提交审核规则。
6. 此处上游随货同行单仅指供应商随采购入库货物提供的单据，不复用 H9 出库随货同行单号、
   截单、打印组套或客户交付语义。
7. 一份上游随货同行单可以关联多个 ASN。从当前 ASN 打开时默认勾选当前 ASN；候选 ASN
   必须同供应商，默认查询当前 ASN 的实际收货当天，操作员可以人工调整收货日期范围。
8. 上游随货同行单支持一个 PDF 或多张 JPG，同一版本内每个文件不超过5MB。上传成功即视为
   已录入，不做图像处理、人工确认或审核。
9. 已上传文件不得原地覆盖。重新上传必须填写修改原因并创建新版本；旧版本文件、修改人、
   修改时间、修改原因和 ASN 关联变化永久保留。
10. 上游随货同行单上传和版本创建支持 `Idempotency-Key`，关联多个 ASN 在同一写入事务中
    完成，并写入 H2 append-only 审计。
11. 清单与上游随货同行单前端验收使用真实 PostgreSQL 数据：E2E 经 API 创建同供应商不同
    收货日期的 ASN，验证默认90天、两个快捷标签 OR 语义、日期调整、多 ASN 关联和刷新后状态；
    截图至少包含清单筛选结果、关联选择和上传后版本记录。

## US-DI-002：药检单独立审核、版本与客户分发副本

**作为** 仓库主管（药检单审核人）
**我要** 独立审核药检单，并生成带货主图章的客户分发副本
**以便** 客户看到的文件经过确认、处理和可追溯的版本控制

### 状态

```text
pending_confirmation（待确认）
  -> confirmed（已确认）
  -> superseded（已被更正替代）
```

### 药检单审核字段表

| 字段 | 必填 | 来源 | 说明 |
|------|------|------|------|
| 药检单版本 ID | 是 | 系统 | 每次更正创建新版本 |
| 原版本 ID | 更正时必填 | 系统 | 形成不可断裂的版本链 |
| 原始文件哈希 | 是 | H-FILE | 证明权威原件未被覆盖 |
| 图像处理方式/版本 | 图片必填 | US-DI-001 | 审核人可改为原色增强 |
| 上传人 | 是 | 系统 | 不得与审核人相同 |
| 审核人 | 是 | 当前用户 | 逐份确认 |
| 审核结论 | 是 | 审核人 | 通过或退回修改 |
| 审核意见 | 退回时必填 | 审核人 | 写入审计 |
| 图章版本 ID | 客户副本必填 | 系统 | 固定确认时生效的图章 |
| 客户副本文件 ID | 生成成功后必填 | H-FILE | 统一为 PDF |
| 客户副本哈希 | 生成成功后必填 | 系统 | 与原件哈希分别保存 |
| 副本生成状态 | 是 | 系统 | 处理中、可用、失败 |

### 验收标准

1. 每份药检单记录单独确认；同一批号的多份记录不能整批代替逐份审核。
2. 上传人和审核人必须是不同用户；系统以稳定 `user_id` 校验，不以姓名比较。
3. `confirmed` 版本不得原地修改。更正时创建新的 `pending_confirmation` 版本，旧版本继续
   作为当前有效版本，直到新版本确认成功。
4. 新版本确认时，在同一事务中将旧版本置为 `superseded` 并切换当前有效版本。
5. 同一 `owner_id + product_id + batch_no` 同一时点最多一个当前有效的 `confirmed` 版本。
6. 默认客户账号只看当前有效版本；具备历史查看设置的账号可以查看原版本、更正版和更正记录。
7. 上传、编辑、提交、退回、确认、复用、更正、重新生成和版本切换全部写入 H2 append-only
   审计，禁止修改或删除历史审计。
8. 审核、退回、更正提交和副本重生成均支持 `Idempotency-Key`，重复请求不得产生重复版本、
   审核结论或后台任务。
9. 审核页面必须以真实 API 和 PostgreSQL 数据完成上传人/审核人双账号 E2E，验证退回、确认、
   更正期间旧版本继续有效、确认后原子切换以及重复提交幂等；截图至少包含待审核详情、退回
   结果、确认后的版本链和审计时间线。

### 货主图章与客户副本验收标准

1. 一个货主同一时间只能有一个生效图章。货主管理员上传透明 PNG，另一名质量负责人审核
   后发布；上传人与审核人必须不同。
2. 图章设计器支持在样例药检单上拖动和等比例缩放。系统保存相对坐标和尺寸比例，同一位置
   应用于全部页面；发布前由配置人和审核人确认未遮挡正文。
3. 图章版本发布后不可改写；新图章只自动用于之后生成的副本，历史副本不静默变化。
4. 客户副本统一生成 PDF：
   - JPG/PNG 保留原始像素宽高和比例，放入 A4 页面，不裁剪；
   - `color_enhance` 使用轻度去噪；
   - `black_white_enhance` 使用自适应二值化和轻度去噪；
   - 中间 JPG 编码质量为 85%；
   - 图像处理完成后再叠加彩色 PNG 图章。
5. PDF 权威原件不做二值化或去噪，只生成盖章分发副本。原 PDF 含数字签名时允许生成副本，
   客户平台页面提示“客户分发副本可能使原数字签名失效”，不把提示写进 PDF 或下载清单。
6. 客户副本默认软上限为 50MB。超过 50MB 时，独立审核人填写原因后可以批准；绝对上限
   为 100MB，超过后必须重新选择处理方式或重新上传。
7. 图像处理结果不清晰时，审核人可以切换为 `color_enhance` 后重新预览，仍须生成盖章副本，
   不得向客户退回未盖章原件。
8. 发布新的处理规则版本时弹窗选择：
   - 仅用于之后确认的药检单；
   - 重新处理当前有效药检单。
   重新处理走后台任务，保留旧副本和哈希；新副本成功后才原子切换，不处理已被替代版本。
9. 药检单确认不等待客户副本生成。副本未就绪或失败不阻塞 WMS 入库、发货；客户平台显示
   “盖章处理中/生成失败”，不得降级提供未盖章原件。
10. 图章与副本前端验收必须上传真实透明 PNG 和真实 JPG/PNG/PDF 样例，通过真实后台任务
    生成客户 PDF 并从 H-FILE 回读；截图至少包含图章拖动/缩放、原图与处理预览、双人发布、
    50MB 超限审批提示和客户副本状态。截图不能以静态占位图代替生成结果。

## US-DI-003：独立客户药检单平台

**作为** 门店用户（下游客户账号）
**我要** 只查询自己获授权地址下已发货或已签收订单的药检单
**以便** 在不影响 WMS 性能的情况下查看和批量下载合规资料

### 客户平台字段表

| 对象 | 字段 | 约束 |
|------|------|------|
| 客户账号 | 用户名、密码哈希、客户 ID、角色、状态 | 独立平台认证，不授予 WMS 权限 |
| 地址范围 | 客户地址 ID 集合 | 普通账号至少绑定一个地址；无地址范围即无数据 |
| 历史权限 | `can_view_report_history` | 默认关闭，可按账号开启 |
| 出库订单 | 订单 ID、状态、客户 ID、`delivery_address_id`、地址快照 | 只同步已发货/已签收订单 |
| 订单行 | 商品 ID、商品名称、批号、数量 | 由实际出库订单投影 |
| 药检单 | 当前版本、客户副本状态、版本链摘要 | 不保存永久下载 URL |
| 导出任务 | 选择范围、文件数、总大小、状态、缺失数、过期时间 | 最多 200 份且不超过 2GB |

### 验收标准

1. 客户平台是独立部署应用和服务，使用独立 PostgreSQL 查询库；客户请求不访问 WMS API
   或 WMS 数据库。
2. WMS 通过既有 H2 outbox/事件能力异步投影客户、地址、已发货/已签收订单、订单行、
   当前确认药检单和客户副本元数据；正常同步目标不超过 30 秒。
3. 事件至少一次投递，客户平台按事件 ID 幂等消费；失败进入重试/DLQ，不阻塞 WMS 作业。
4. 客户使用用户名和密码登录。客户管理员可以管理本客户账号并查看全部客户地址。
5. 普通客户账号可以绑定一个或多个客户地址；查询必须同时满足客户 ID 和地址 ID 范围，
   未绑定地址时不返回任何订单或药检单。
6. M4 出库订单必须保存稳定 `delivery_address_id` 和不可变地址快照。客户平台只展示
   `已发货`、`已签收`订单。
7. 客户从订单进入商品和批号明细，再查看对应的当前有效药检单。没有可用客户副本时显示
   “资料暂缺”或具体处理中状态，不影响 WMS 发货。
8. 默认只展示当前有效版本；账号开启历史查看后，页面才显示原版本、更正版和更正记录。
9. 客户平台前端验收必须启动独立客户 Web、服务和 PostgreSQL 查询库，以真实投影事件创建
   客户、两个地址、不同状态订单和报告版本；Playwright 不得访问 WMS API 或拦截业务请求。
10. E2E 使用客户管理员、普通多地址账号、无地址账号和历史权限账号分别登录，截图至少包含
    地址范围查询、订单批号详情、资料处理中、历史版本可见/不可见和越权无数据结果。

### 单份与批量下载验收标准

1. 单份查看或下载前，客户平台以本地查询库重新校验客户、地址、订单、商品和批号范围。
2. 校验通过后签发 **15 分钟有效的下载会话（token）**，返回客户平台相对路径
   `/api/v1/files/{token}`（非对象存储预签名 URL）。浏览器向 **客户平台下载接口**
   再次请求时，服务在校验会话未过期后 **流式读取** H-FILE 只读根（测试实现为本地盘
   或挂载卷；生产映射同一 H-FILE 语义）并回传文件字节。整条链路 **不访问 WMS API 或
   WMS 数据库**。会话过期不删除文件，客户再次点击授权即可签发新会话。
   单份下载和 ZIP 内文件统一命名为 `{药品名}_{商品编码}_{批号}_药检单_V{版本号}.pdf`，
   文件名特殊字符替换为 `_`；ZIP 内同名冲突从第二份起在扩展名前追加 `_2`、`_3` 等序号。
3. 客户可以勾选多个订单生成一个 ZIP。相同当前药检单版本被多个订单引用时，ZIP 内只放
   一份文件。
4. ZIP 包含药检单 PDF 和清单 CSV/XLSX。清单记录订单号、地址、商品、批号、报告版本、
   文件名和状态；缺失资料列为“资料暂缺”，不得静默遗漏或阻塞已有文件下载。
5. 批量任务在独立客户平台后台异步生成，单次最多 200 份且总计不超过 2GB；超出时提示
   拆分任务。
6. 导出结果进入“导出中心”并通过页面消息提示完成。ZIP 写入 H-FILE `wms-exports`
   客户平台专属前缀，保留 7 天；每次下载仍先签发 15 分钟下载会话，再经客户平台流式回传。
7. 客户平台主服务对 `wms-attachments` 只读；导出任务仅获得读取授权附件和读写自身
   `wms-exports` 前缀的最小权限。
8. 有历史查看设置的账号可以选择“包含历史版本”，默认关闭；未授权账号不能通过批量任务
   绕过历史限制。
9. 登录、查询、查看、单份下载、批量导出创建和 ZIP 下载写入客户平台审计；WMS 同步投递
   继续写 H2 审计，不在日志或审计 diff 中记录文件正文、密码或完整下载 token/URL。
10. 下载验收必须使用 H-FILE 测试实现（或生产等价只读存储根）签发 15 分钟下载会话并生成
    真实 ZIP；E2E 校验会话过期重签、ZIP 去重、缺失清单、200份/2GB 拒绝、7天导出记录和
    地址/历史权限；截图至少包含单份下载授权、批量任务、导出中心完成及超限提示。
    首期基线不要求浏览器直连对象存储预签名 URL；后续若升级为预签名直出，不得放宽
    鉴权与地址/历史范围校验。

## US-DI-004：药检单有效性与质量联动

**作为** WMS 系统
**我要** 在入库验收时校验各批号的有效药检单和检验结论
**以便** 缺失或不合格时按受控质量流程处理

### 验收标准

1. 只有当前有效的 `confirmed` 药检单版本参与有效性判断；待确认和已被替代版本不算齐全。
2. 验收提交时按 ASN 的每个批号检查药检单；缺失时由 M-VR 货主规则决定警告或阻塞。
3. 药检结论不合格时，自动创建 M-QL 质量联系单并阻塞对应批次验收；M-DI 不直接修改库存。
4. M-QL 审批完成后，由 M-QL 调用 M3 库存状态变更，明确携带审批源
   `approval_source = quality_liaison` 和质量联系单 ID。
5. 规则可以受控配置哪些商品类别必须有药检单；规则版本和校验结果保存到验收记录。
6. 客户资料缺失、客户副本处理中或盖章失败均不增加 M4 发货阻塞；客户平台继续显示
   “资料暂缺/处理中”，资料完成后异步补齐。
7. 校验、联系单创建和重试支持幂等；规则命中、异常和处置写入 H2 审计。
8. 前端联动验收使用真实 M2/M-DI/M-VR/M-QL/PostgreSQL 数据，分别验证缺失警告、缺失阻塞、
   不合格自动联系单、审批后库存状态变化，以及客户副本失败仍可发货；截图至少包含验收阻塞、
   质量联系单和允许发货三种结果。

## 跨故事约束

1. 权威原件、药检单版本和客户分发副本是三个不同事实：原件不可变，版本可被更正替代，
   副本可按固定的处理规则和图章版本重新生成。
2. H9 的 `external_file` 药检单继续引用权威原件；客户分发副本不自动替代 H9 打印事实源。
3. 所有业务查询和事件投影必须带 `owner_id`；客户平台再叠加 `customer_id` 和
   `delivery_address_id` 范围。
4. 所有写操作必须满足 L4、L5、L8、L11；药检单审核、版本切换、图章发布和客户下载还要
   覆盖审计合规与并发一致性。
5. 客户平台、对象存储或副本处理故障不得降低 WMS 入库、库存和出库 API 的可用性。

### 前端真实 E2E 与截图证据

1. “真实 E2E”是指浏览器连接本轮构建的真实前端、真实 HTTP 服务和独立 PostgreSQL 测试库；
   写操作还必须连接 H-FILE/对象存储测试实现及真实后台任务。禁止把 dev mock、静态 JSON、
   `page.route` 业务响应拦截或只存在浏览器内存的数据称为真实 E2E。
2. 测试数据必须由 API、事件入口或数据库夹具在测试开始时创建，并带本轮唯一标识；测试结束
   后可按既有测试库清理策略回收，不使用生产数据。
3. 每个前端验收场景必须同时断言页面结果和刷新后的持久化结果；涉及权限时使用真实不同账号，
   涉及隔离时使用不同货主、客户或地址数据。
4. 每个有前端交互的故事都必须在 `governance/quality-matrix.toml` 登记真实 Playwright 命令、

   `evidence_refs`。开发 Mock 截图只用于走查，不进入验收完成证据。
5. 截图必须由通过的 E2E 在业务断言之后生成，覆盖正常结果、关键拒绝/越权结果和版本/审计
   结果；仅截图页面外观而未验证真实数据链路，不算通过。
