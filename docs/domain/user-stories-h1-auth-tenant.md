# 用户故事：H1 权限与多租户（auth-tenant）

> 模块：H1 横向能力 / Wave 1 W1.A
> 性质：所有业务模块的鉴权基础
> 依赖：无（最底层基础设施）
> 关联 ADR：0001（技术栈）、0006（TDD）、ADR-0008（借鉴 Odoo ADR-0008 §6 ir.rule 行级访问控制）、ADR-0024（JWT + AuthContext + 多租户隔离）

---

## 背景

WMS 服务多个货主（3PL 模式），所有 API 必须鉴权 + 数据按货主隔离。
角色由 M1-006 定义（8 角色），权限由本模块管理。

---

## 跨故事约束

1. **审计追踪**：登录、登出、权限变更、token 失效均写入 H2 审计追踪
2. **token 安全**：JWT 签名密钥安全存储；Access Token 默认 1 小时、Refresh Token 默认 24 小时（ADR-0024 §2.2）；token 过期后强制重新登录
3. **多货主隔离**：所有业务读写必须使用 `AuthContext.owner_id` 过滤；PostgreSQL RLS 延后到 Wave 2+ 评估（ADR-0024 §2.7），Wave 1 不把 RLS 作为完成前提
4. **GSP 合规**：用户停用立即失效（不延迟）；密码符合 GSP 计算机系统操作权限要求
5. **幂等性**：所有写操作支持 Idempotency-Key
6. **API Key 生命周期**：外部系统 API Key 的创建、轮换、吊销、作用域、过期策略由 US-H1-006 统一管理
7. **PDA 离线冲突统一策略**（v3.1 新增，C1；适用于所有 PDA 写操作故事）：
   - **情形 A 普通离线**（同步时数据一致）：PDA 本地暂存 → 网络恢复后按提交时间序自动同步；同步成功后清理本地缓存；token 仍有效则跳过重新登录
   - **情形 B 离线冲突**（同步时发现服务端数据已变）：PDA 暂存的操作不自动覆盖；自动创建"待主管处理"事件 → 推送仓库主管企业微信（H4）→ 主管选择「丢弃 PDA 操作 / 强制覆盖（带强制理由）/ 部分合并」
   - **离线时长上限**：默认 24 小时（可配置）；超过该时长 PDA 强制要求联网才能提交
   - **审计标识**：所有离线同步的操作在 H2 审计追踪中带 `is_offline_submission = true`
   - 各 PDA 故事（M2-002/M2-003/M2-005/M3-004/M3-005/M4-003/M-DI-002/M-TE-008）的离线条款参照本策略执行
8. **测试要求**：写操作必须含 L4（错误路径）+ L5（数据一致）+ L8（权限）+ L11（幂等）

## US-H1-001：用户登录与 token 签发

**作为** 任意 WMS 用户
**我要** 用工号/手机号 + 密码（或工牌扫码）登录系统
**以便** 获得访问令牌，进入业务模块

### 验收标准

1. **登录方式**：
   - 工号 + 密码（PC/PAD 主用）
   - 手机号 + 短信验证码（备用 + 移动端）
   - 工牌扫码（PDA 主用，扫码 = 工号 + 设备指纹）
2. **密码规则**（M1-006 v13 已声明可配置）：
   - 默认最小长度 8
   - 默认含大小写字母 + 数字
   - 默认 90 天过期需修改（可配置）
3. **登录失败保护**：连续 5 次失败 → 锁定账号 15 分钟（默认值，可配置）
4. **token 签发**：JWT；Access Token 默认 1 小时（可配置）；Refresh Token 默认 24 小时（可配置）
5. **token 内容**：`sub/user_id` / `owner_id` / `user_name` / `permissions` / `jti` / `iat` / `exp`
6. **多货主用户**：用户可绑定多个货主（3PL 员工）；Access Token 仅包含当前激活 `owner_id`，货主切换时重签 token
7. **审计**：actor = user_id，记录登录时间、IP、设备指纹、登录方式、成功/失败
8. **离线 token 缓存**：移动端登录后本地缓存 token 直到过期，支持离线鉴权

## US-H1-002：角色与权限管理

**作为** 系统管理员
**我要** 管理角色（M1-006 8 角色）的菜单权限和按钮级操作权限
**以便** 不同岗位看到/操作各自范围

### 验收标准

1. **角色清单**（M1-006 唯一来源）：8 角色（系统管理员/仓库主管/收货员/养护员/保管员/货主/门店用户/司机）
2. **权限粒度**：
   - 菜单可见性（树形结构对应 mkdocs/PC 端导航）
   - 按钮级操作权限（如"创建 ASN" / "审批退货" / "强制通过"）
   - 数据范围（自己 / 本仓 / 本货主 / 全部）
3. **权限矩阵默认模板**：每个角色都有开箱默认权限集：
   - 系统管理员：全局配置、用户权限、API Key、审计查询
   - 仓库主管：业务单据审批、异常处理、库存/报表查询
   - 收货员：ASN 收货、PDA 验收、药检单关联
   - 养护员：养护任务、养护记录、异常上报
   - 保管员：上架、移库、拣选、复核、包装
   - 货主：本货主订单/库存/报表只读查询
   - 门店用户：门店订货、签收、订单/温控查询
   - 司机：配送任务、在途异常、到店签收
4. **权限继承**：子岗位（保管员-复核岗）继承父岗位（保管员）+ 增减
5. **多角色叠加**：用户可有多角色，权限取并集
6. **批量授权**：管理员可批量为多用户授角色
7. **权限即时生效**：变更后下次 API 调用即生效（旧 token 命中 `permissions_changed_at` → 401 `AUTH-009` → 强制重新登录）
8. **审计**：actor = 管理员 user_id，记录角色/权限变更详情

## US-H1-003：API 鉴权中间件

**作为** WMS 后端开发者
**我要** 一个统一鉴权中间件，所有受保护的 API 自动鉴权
**以便** 业务代码不重复写鉴权逻辑

### 验收标准

1. **请求鉴权**：从 `Authorization: Bearer <token>` 头部解析；缺失 / 过期 / 签名错误 → 401
2. **权限校验**：
   - API 注解声明所需权限（如 `#[require("inbound:create")]`）
   - 中间件检查 token 中权限列表是否包含
   - 不包含 → 403 + 写审计（actor / 路径 / 缺失权限）
3. **多货主上下文注入**：从 token 提取 `owner_id` 注入 `AuthContext`，业务代码必须用该上下文查询库存
4. **token 刷新**：客户端可用 refresh token 换取新 access token；refresh token 无效或过期返回 `AUTH-007`；权限变更命中 `AUTH-009` 时强制重新登录
5. **API Key 鉴权**（外部系统）：
   - 与用户 token 区分（actor 标识为 API Key ID + 调用方名称，不记录明文密钥）
   - API Key 必须由 US-H1-006 创建并绑定作用域、货主、过期时间
   - 支持限流（默认 100 QPS / 单 Key，可配置）
   - 写审计（actor = API Key ID，含调用方名称）
6. **测试覆盖**（L8 权限）：
   - 无 token / 错 token / 过期 token → 401
   - 有 token 无权限 → 403 + 审计写入
   - 跨货主访问 → 403
7. **性能**：鉴权中间件 P99 延迟 ≤ 5 ms（默认值，监控阈值）

## US-H1-004：多货主数据隔离

**作为** 系统架构师 / 货主
**我要** 多货主数据在数据库层逻辑隔离，业务代码不可能跨货主访问
**以便** 满足 3PL 数据安全 + GSP 合规

### 验收标准

1. **逻辑隔离**：所有业务表含货主隔离字段（`owner_id`；落表命名可按字段词典映射）
2. **Wave 1 隔离方式**：业务 handler 必须使用 `AuthContext.owner_id` 过滤查询与写入；PostgreSQL RLS 延后到 Wave 2+ 评估
3. **货主切换**：多货主用户切换 active owner → 重签 token
4. **跨货主可见性**（少数场景）：仓库主管可"全货主视图"权限（如总仓盘点统计），需特殊角色 + 二次确认
5. **API 接口**：货主在 URL/参数中显式声明 → 中间件校验当前用户对该货主有权限，并与 `AuthContext.owner_id` 对齐
6. **数据导出**：导出数据自动按 tenant 切片；不允许混合导出多货主数据
7. **测试覆盖**（L8 + L5）：
   - 货主 A 用户查询货主 B 数据 → 0 结果（不暴露存在性）
   - 物理隔离切换：可配置某货主使用独立 schema/database（v15 苏格拉底自问待续，Wave 5 落地）
8. **审计**：actor 含 `owner_id`，所有审计可按货主切片查询

## US-H1-005：Token 失效与登出

**作为** WMS 用户 / 系统管理员
**我要** 登出后立即失效 token；管理员强制踢人立即生效
**以便** 满足 GSP "用户停用立即失效" + 操作安全

### 验收标准

1. **用户主动登出**：客户端调用登出 API → token 加入"黑名单"立即失效
2. **被动失效**：
   - token 过期（自然失效）
   - 用户密码修改
   - 用户停用
   - 角色权限变更（`AUTH-009`，强制重新登录）
3. **黑名单存储**：Redis 短期缓存（直到 token 自然过期），不影响数据库
4. **管理员强制踢人**：调用"踢出用户"API → 该用户所有 token 失效 → 客户端下次请求被拒强制重登
5. **多设备会话管理**：用户可在"会话列表"看到自己所有活跃登录（设备 + IP + 登录时间），可单独失效某设备
6. **审计**：失效原因（主动 / 强制 / 修改密码 / 角色变更）+ 触发人（自己 / 管理员 user_id）
7. **GSP 合规**：用户停用 → 正常 Redis 可用路径下所有 token 失效延迟 ≤ 1 秒；Redis 故障降级按 ADR-0024 §2.3.1 执行并触发 P1 告警

## US-H1-006：API Key 生命周期管理

**作为** 系统管理员
**我要** 为外部系统创建、轮换、吊销 API Key，并配置调用范围
**以便** ERP、采购平台、码上放心、药检平台等外部系统接入时具备可审计、可撤销、最小权限的访问控制

### 验收标准

1. **创建 API Key**：必填调用方名称、用途、所属货主/仓库范围、权限作用域、过期时间、负责人
2. **密钥展示规则**：明文密钥只在创建时展示一次；数据库只保存哈希值和 key_id
3. **作用域控制**：每个 Key 只能访问被授权的 API 范围（如 `master-data:write` / `inbound:push` / `tms:callback`）
4. **轮换机制**：支持生成新 Key 并设置旧 Key 宽限期；默认宽限期 7 天，可配置
5. **吊销机制**：系统管理员可立即吊销 Key；吊销后所有请求返回 401，并写入审计追踪
6. **过期策略**：默认有效期 180 天，可配置；到期前 30 天通过 H4 企业微信通知负责人
7. **调用审计**：记录 key_id、调用方名称、API 路径、请求时间、来源 IP、响应状态、关联货主；不记录密钥明文
8. **异常保护**：同一 Key 连续鉴权失败 10 次或超过限流阈值时自动临时禁用 15 分钟，并通知系统管理员
9. **多货主隔离**：Key 绑定货主范围；跨授权货主访问返回 403，且不暴露目标数据是否存在
10. **幂等性**：创建、轮换、吊销操作支持 Idempotency-Key，重复提交不产生重复 Key

## US-H1-007：PC 管理端三层菜单管理

**作为** 系统管理员
**我要** 在 PC 管理端维护全局三层菜单、页面绑定和按钮权限点
**以便** 管理端导航、角色菜单权限和按钮权限使用同一菜单来源

### 验收标准

1. **三层结构**：菜单固定为 `业务域 -> 能力组 -> 页面`，不允许超过三层。
2. **全局统一**：菜单结构全局唯一，货主不覆盖菜单结构；货主差异由权限、字段配置和业务参数处理。
3. **数据库存储**：菜单使用邻接表模型，字段包含 `parent_id`、`level`、`code`、`path`、`title`、`view_id`、`icon_key`、`permission_key`、`sort_order`、`enabled`。
4. **页面绑定**：三级菜单只能绑定前端已注册的 `view_id`，未注册不能发布。
5. **图标安全**：后端只保存 `icon_key`，前端用 lucide 图标白名单渲染，不保存 SVG / HTML。
6. **草稿发布**：菜单编辑先进入草稿，点击发布后一次性生效；发布前校验层级、唯一性、`view_id`、权限键和排序。
7. **版本回滚**：每次发布生成菜单版本；系统管理员可回滚上一发布版本。
8. **菜单管理页面**：入口为 `基础能力 -> 平台能力 -> H1 菜单管理`，支持树形展示、新增、编辑、拖拽排序、拖拽换父级、批量启停、发布、回滚。
9. **按钮权限点**：菜单节点下维护按钮权限点；初版来源为内置标准动作（新增、编辑、删除、启停、详情、查询、刷新、导出、打印、汇总、字段、视图）和页面私有动作。
10. **权限**：仅系统管理员可维护菜单草稿、发布和回滚；普通用户只能读取已发布且自己有权限的菜单。
11. **审计**：新增、编辑、批量启停、发布、回滚必须写入 H2 审计追踪。
12. **幂等性**：所有写操作支持 Idempotency-Key，重复提交返回首次结果，不重复创建节点或版本。

### 测试维度覆盖

#### US-H1-001 登录与 token 签发

| 维度 | 场景 |
|------|------|
| L4 错误路径 | 工号不存在 → H1_AUTH_USER_NOT_FOUND; 密码错误 → H1_AUTH_INVALID_CREDENTIALS; 账号锁定 → H1_AUTH_ACCOUNT_LOCKED; 短信验证码过期 → H1_AUTH_CODE_EXPIRED |
| L5 数据一致 | 登录失败计数 + 锁定状态必须原子更新；token 签发与 refresh token 写入同一事务 |
| L8 权限 | 停用用户登录 → 401; 锁定用户登录 → 401 + 提示剩余锁定时间 |
| L11 幂等 | 相同凭据重复登录 → 每次签发新 token（登录不幂等，但不产生副作用重复） |

#### US-H1-002 角色与权限管理

| 维度 | 场景 |
|------|------|
| L4 错误路径 | 角色名重复 → H1_ROLE_DUPLICATE; 删除已绑定用户的角色 → H1_ROLE_IN_USE; 权限码不存在 → H1_PERMISSION_NOT_FOUND |
| L5 数据一致 | 角色-权限关联批量更新原子；权限变更后 token 缓存立即失效 |
| L8 权限 | 仅系统管理员可操作；非管理员调用 → 403 |
| L11 幂等 | 相同 Idempotency-Key 重复提交角色创建 → 返回首次结果，不重复创建 |

#### US-H1-003 API 鉴权中间件

| 维度 | 场景 |
|------|------|
| L4 错误路径 | 无 Authorization 头 → 401; token 签名错误 → 401; token 过期 → 401 + retry_hint=fast; 权限不足 → 403 |
| L5 数据一致 | `AuthContext.owner_id` 注入与 handler 查询过滤一致；中间件拒绝后审计写入不可丢失 |
| L8 权限 | 每个 API 注解声明所需权限；未声明的 API 默认拒绝（白名单模式） |
| L11 幂等 | 中间件本身无状态，不涉及幂等（透传到业务层） |

#### US-H1-004 多货主数据隔离

| 维度 | 场景 |
|------|------|
| L4 错误路径 | handler 未使用 `AuthContext.owner_id` 过滤 → 测试失败 / 审计对账告警；切换到未授权货主 → 403 |
| L5 数据一致 | 查询条件与 token 中 `owner_id` 严格一致；跨货主事务不可能成功 |
| L8 权限 | 货主 A 用户查询货主 B 数据 → 0 结果（不暴露存在性）; 全货主视图需特殊角色 + 二次确认 |
| L11 幂等 | 货主切换（重签 token）幂等：相同请求返回相同新 token |

#### US-H1-005 Token 失效与登出

| 维度 | 场景 |
|------|------|
| L4 错误路径 | 登出已失效 token → 200（幂等，不报错）; 踢出不存在用户 → H1_USER_NOT_FOUND; Redis 不可用 → 按 ADR-0024 §2.3.1 fail-open 并告警 |
| L5 数据一致 | 黑名单写入 Redis + 审计写入 PG 必须都成功；Redis 失败时保留审计与告警，接受最长 access TTL 的撤销窗口 |
| L8 权限 | 用户只能登出自己；管理员可踢任何人；非管理员踢他人 → 403 |
| L11 幂等 | 重复登出同一 token → 200（已在黑名单，幂等返回） |

#### US-H1-006 API Key 生命周期管理

| 维度 | 场景 |
|------|------|
| L4 错误路径 | 作用域不合法 → H1_APIKEY_INVALID_SCOPE; 过期时间 < 当前时间 → H1_APIKEY_INVALID_EXPIRY; 吊销已吊销的 Key → 200（幂等） |
| L5 数据一致 | 创建 Key 时哈希值 + 元数据写入同一事务；轮换时新旧 Key 状态原子切换 |
| L8 权限 | 仅系统管理员可创建/轮换/吊销；Key 绑定货主范围，跨授权货主 → 403 |
| L11 幂等 | 创建/轮换/吊销均支持 Idempotency-Key；重复提交返回首次结果 |

#### US-H1-007 PC 管理端三层菜单管理

| 维度 | 场景 |
|------|------|
| L4 错误路径 | 发布存在第四层菜单 → H1_MENU_INVALID_TREE; 三级菜单绑定未知 `view_id` → H1_MENU_UNKNOWN_VIEW; 图标不在白名单 → H1_MENU_INVALID_ICON |
| L5 数据一致 | 发布时草稿节点、按钮权限点、版本头和版本节点快照在同一事务中写入 |
| L8 权限 | 仅系统管理员可维护草稿、发布和回滚；普通用户只能读取已发布且自己有权限的菜单 |
| L11 幂等 | 相同 Idempotency-Key 重复新增、批量启停、发布、回滚返回首次结果，不重复创建节点或版本 |

### PDA 弹性

> 适用故事：US-H1-001（工牌扫码登录）、US-H1-002（PDA 端权限刷新）

#### 离线策略

| 场景 | 行为 |
|------|------|
| PDA 已有有效 token + 断网 | 本地缓存 token 继续使用；离线鉴权（本地校验签名 + 过期时间） |
| PDA token 过期 + 断网 | 提示"网络不可用，无法刷新登录"；允许查看本地已缓存数据（只读） |
| 网络恢复 | 自动尝试 refresh token；成功 → 恢复正常；失败 → 强制重新登录 |

#### 扫码交互

| 场景 | 行为 |
|------|------|
| 工牌扫码登录 | 扫描工牌二维码 → 解析工号 + 设备指纹 → 调用登录 API |
| 扫码失败（模糊/损坏） | 提示"扫码失败，请重试或手动输入工号" |
| 非工牌码 | 提示"无效工牌码" |

#### 异常恢复

| 场景 | 行为 |
|------|------|
| 登录过程中 APP 崩溃 | 重启后检查本地 token → 有效则直接进入；无效则重新登录 |
| 权限刷新过程中断网 | 使用旧权限继续操作（直到 token 过期）；网络恢复后自动刷新 |
| 多设备冲突（同一用户） | 后登录设备生效；前设备下次请求被拒 → 提示"已在其他设备登录" |

## 业务边界声明

> H1 权限模块的边界：
>
> 1. **角色单一来源**：M1-006 是唯一角色定义；本模块不重复定义
> 2. **不主管业务规则**：本模块只做"能做什么"（权限），不做"做了什么"（业务逻辑）
> 3. **审计接收方**：本模块产生审计事件，写入由 H2 处理
> 4. **多租户**：v3 决策 = 逻辑隔离为主 + 物理隔离可选（详见 docs/concept-audit.md 镜头 5）
> 5. **不主管 GSP 业务条款**：仅满足 GSP 5.66 不同岗位权限要求 + 5.72 修改可追溯（与 H2 配合）
