# 用户故事：H2 审计追踪基础设施（audit-trail）

> 模块：H2 横向能力 / Wave 1 W1.B
> 性质：所有业务模块的审计基础（与 H10 数据库备份共同保障 GSP 数据完整性）
> 依赖：H1 权限（actor 来源）
> 关联 ADR：0006（TDD）

---

## 背景

GSP 5.62-5.75 要求计算机系统操作可追溯、不可篡改。本模块为所有业务写操作提供统一的审计追踪记录服务，append-only 存储，保留 ≥ 5 年。

---

## 跨故事约束

1. **append-only 不变量**：审计表只能 INSERT，禁止 UPDATE/DELETE（数据库层 trigger + 应用层校验双保险）
2. **多货主隔离**：审计表含 tenant_id；货主只能查自己的审计
3. **GSP 合规**：保留 ≥ 5 年；审计表数据由 H10 数据库备份覆盖
4. **幂等性**：相同 idempotency_key 的写操作产生 1 条审计记录
5. **性能**：审计写入异步入队（不阻塞业务）；P99 延迟 ≤ 50 ms 落库
6. 测试要求：写操作必须含 L4（错误路径）+ L5（数据一致）+ L8（权限）+ L11（幂等）；读操作必须含 L4 + L8

## US-H2-001：审计事件统一记录

**作为** 业务模块开发者
**我要** 一个统一的审计接口，写操作时调用即可
**以便** 不重复写审计逻辑、保证审计字段完整

### 验收标准

1. **统一接口**：
   ```rust
   audit::record(AuditEvent {
       actor: UserContext,        // 来自 H1 注入
       action: &str,              // 如 "create_asn" / "approve_return"
       resource_type: &str,       // "asn" / "order" / "stock"
       resource_id: &str,         // 业务 ID
       old_value: Option<Json>,
       new_value: Option<Json>,
       reason: Option<String>,
       approval_source: Option<String>,  // M3-003 6 类枚举之一（v13 升 7 类）
       approval_id: Option<String>,
       ip: String,                // 自动捕获
       user_agent: String,        // 自动捕获
       idempotency_key: Option<String>,
   })
   ```
2. **必填字段**：actor / action / resource_type / resource_id / 时间戳（系统补）
3. **22 类操作枚举**（M6-002 v8 已定义，本模块作为执行端）
4. **审批源枚举**（M3-003 v13 7 类）
5. **审计写入**：异步队列（默认）+ 关键路径同步选项（金额变更等）
6. **失败重试**：写入失败 3 次后告警 + 进入死信队列；不允许业务回滚（业务已成功不能因审计失败回滚）
7. **审计本身不审计**：避免无限递归
8. **测试覆盖**：写入异常路径（数据库连接失败 / 队列满）+ 幂等性（同 key 不重复）

## US-H2-002：审计追踪查询

**作为** 仓库主管 / 系统管理员 / 监管检查员
**我要** 多维度查询审计追踪记录
**以便** 追溯问题、满足 GSP 检查、内审

> 注：本故事承接 [M6-002 审计追踪查询](user-stories-m6-audit-report.md#us-m6-002) 的查询界面，本故事提供后端实现。

### 验收标准

1. **查询维度**：
   - actor / 时间范围 / action 类型 / resource_type / resource_id / approval_source
   - 货主（多货主隔离）
   - 通过审计追踪反查业务实体（如"该订单的所有审计事件"）
2. **结果字段**：完整审计 record + 业务实体快照（旧值/新值）
3. **导出**：CSV / PDF（GSP 法定台账格式）
4. **性能**：典型查询（30 天范围）P99 ≤ 2 秒；归档数据查询提示"涉及归档分区，预计 N 秒"
5. **大数据量**：默认分页 100 条；可流式导出
6. **权限**：用户只能查自己的；仓库主管查本仓所有；系统管理员查全部
7. **审计的审计**：查询 / 导出操作记录到独立的"审计访问日志"
8. **追溯码反查链路**（关键场景）：扫一个追溯码 → 查到所有相关审计事件（入库 / 出库 / 状态变更）

## US-H2-003：append-only 不变量保护

**作为** 系统架构师 / 监管检查员
**我要** 数据库层强制审计表只能 INSERT
**以便** 即使应用代码有 bug 或 DBA 误操作，审计表也无法被篡改

### 验收标准

1. **数据库 trigger**：审计表 BEFORE UPDATE/DELETE → RAISE EXCEPTION
2. **应用层校验**：ORM/SQL 模板不允许 UPDATE/DELETE 审计表
3. **DBA 权限**：生产环境 DB 用户对审计表无 UPDATE/DELETE 权限（仅系统服务账号可 INSERT）
4. **超级管理员**：极端场景（误录数据需更正）通过新增"更正"审计记录实现，不修改原记录
5. **测试覆盖**：
   - 直接 SQL UPDATE 审计表 → 失败
   - 直接 SQL DELETE 审计表 → 失败
   - 通过 ORM 任何更新方法 → 失败（编译期检查更佳）
6. **GSP 合规**：满足 5.67（数据原始性）+ 5.72（修改可追溯）+ 5.75（操作记录不可篡改）

## US-H2-004：审计数据归档与保留

**作为** 系统管理员 / GSP 审计员
**我要** 审计数据分区存储 + 自动归档 + 5 年保留
**以便** 满足 GSP 同时控制存储成本

### 验收标准

1. **分区策略**：审计表**按季度分区**（PostgreSQL 原生分区，详见 [docs/infra/sharding-decision-matrix.md](../infra/sharding-decision-matrix.md) v1.2 §3.2）
2. **保留策略**：
   - 在线分区：最近 4 个季度（高频查询）
   - 归档分区：4 个季度以上（只读，查询慢一档）
   - 总保留 ≥ 5 年（GSP 强制）
3. **自动归档作业**：每季度首日凌晨执行（默认值，可配置）
4. **归档查询**：透明（用户无感）但提示"涉及归档分区，预计 N 秒"
5. **5 年到期**：超期数据**仍不删除**（GSP 要求"不删除，只归档"）；移到深度归档（OLAP / 冷存储）
6. **关联备份**：归档数据由 H10 数据库备份覆盖（v11）
7. **监控**：分区大小、归档延迟、查询延迟监控
8. **审计的审计**：归档作业本身写审计（actor=`system-archive`）

## US-H2-005：事件总线（审计事件订阅 / H-EVT 通用能力）

**作为** 业务模块开发者 / 监管对接服务
**我要** 通过统一的事件总线发布与订阅业务事件 + 审计事件，实现跨模块解耦联动
**以便** 模块间通信不依赖直接调用 + 联动一致性可保证 + 失败可重试可重放

### 设计原则（v3.1 升级）

本故事是 wms **统一事件总线**（H-EVT 角色），覆盖三类事件源：

1. **审计事件**（H2 主体）：所有写操作经过 H2-001 后自动发布到事件总线
2. **业务事件**（业务模块发布）：状态迁移 / 库存变更 / 温度超标 / 资质过期 等
3. **系统事件**（基础设施发布）：归档完成 / 备份完成 / 配置变更 等

**关键决策**：不为业务事件单独建 H-EVT 模块，统一在本故事承载——审计事件与业务事件共享同一个发布订阅基础设施，避免概念分裂。

### 验收标准

1. **订阅模型**：发布订阅模式（PostgreSQL LISTEN/NOTIFY 或 Kafka，由 ADR 决策）
2. **事件分类与命名**：
   - 审计事件：`audit.<resource_type>.<action>`（如 `audit.inventory.status_change`）
   - 业务事件：`business.<module>.<event>`（如 `business.cold_chain.temp_exceeded` / `business.dock.appointment_arrived`）
   - 系统事件：`system.<source>.<event>`（如 `system.archive.completed`）
3. **订阅维度**：事件类型 + tenant_id + resource_type + 任意自定义过滤条件
4. **订阅者示例**：
   - M-VR 规则引擎：订阅"上架完成"事件触发 ABC 重算
   - M-QL 联系单：订阅"温度超标事件"自动创建养护异常联系单
   - H4 通知：订阅"审批待处理"事件推送企业微信
   - H-DOCK 看板：订阅"预约状态变更"事件实时刷新月台看板
   - H-AL 告警引擎：订阅"养护超期 / 资质过期 / 备份失败"等事件触发告警
5. **可靠投递**：at-least-once（订阅者处理幂等）；订阅者处理失败可重试（默认 3 次指数退避，可配置）
6. **订阅生命周期**：
   - 注册（含订阅者标识 / 过滤条件 / 处理 webhook 或函数引用）
   - 接收事件 → ack / nack
   - 退订
   - 订阅失败有**死信队列**（DLQ）+ 仓库主管告警
7. **事件回放**：可按事件类型 + 时间范围回放（用于订阅者首次启用 / 故障恢复 / 监管补报）；回放需双人审批（管理员 + 仓库主管）
8. **测试覆盖**：
   - L11 幂等：同事件多次投递 → 订阅者处理一致
   - L4 错误路径：订阅者失败 → 死信队列入队 + 告警
   - L10 可观测：事件吞吐 / 投递延迟 / 失败率指标暴露
9. **性能**：事件投递 P99 ≤ 100 ms（订阅者从消费到 ack）
10. **审计**：订阅注册/退订/事件回放写审计

### 异常路径

- 订阅者处理超时（默认 30s，可配置）→ 自动 nack + 重试
- 死信队列积压超阈值（默认 1000 条）→ H-AL 告警
- 事件总线本身故障 → 业务模块降级为同步执行 + 告警

### 与其他模块的关系

| 模块 | 关系 |
|---|---|
| H2-001 审计统一记录 | 所有写操作 → H2-001 → 自动发布到本事件总线（审计事件） |
| H4 企业微信通知 | 订阅事件后调用 H4 发送通知（H4 = 通道，本模块 = 路由） |
| H-AL 告警引擎 | 订阅事件后按规则触发告警（H-AL = 告警业务逻辑） |
| H8 ERP 防腐层 | ERP 反馈通过本总线异步通知业务模块 |
| H-DOCK / H-Store / 业务模块 | 发布业务事件到本总线，订阅其他模块事件实现联动 |

## US-H2-006：业务数据生命周期归档

**作为** 系统管理员 / GSP 审计员
**我要** 业务数据按字段类别和合规要求差异化归档，不只是审计数据
**以便** 全系统数据生命周期满足 GSP 各类保留期要求 + 控制在线库存储成本

### 背景

H2-004 只覆盖**审计数据**的归档；GSP 5.67 / 7.107 / 8.122 / 特-2 / 追-3 对**业务数据**也有保留期要求，且按数据类型差异化：

| 数据类别 | GSP 条款 | 保留期 |
|---|---|---|
| 普通药品业务数据（库存/订单/ASN/出库流水）| 5.67 / 8.122 | ≥ 5 年 |
| 特殊药品（麻精毒放）销毁 / 流通台账 | 特-2 / 7.107 | ≥ 30 年 |
| 追溯码上报记录 | 追-3 | ≥ 5 年 |
| 冷链温湿度记录 + 超标事件 | 7.91 / 冷-7 | ≥ 5 年（同有效期+1 年）|
| 不合格品销毁记录 | 7.103 | ≥ 5 年 |
| 客商资质副本 | 6.79 / 6.80 | 资质有效期 + 5 年 |
| 主数据（商品/客户/供应商）| — | 永久（不归档）|
| 系统配置变更 | 5.69 | ≥ 3 年 |

### 验收标准

1. **归档分级**：所有业务表按 §6 字段词典 `field_class` + `audit_required` + 业务类型标识其保留期，统一定义在配置中心：

   - 在线层（高频查询）：默认 12 个月（可配置 `inline_retention_months`）
   - 归档层（只读）：在线层后 → 配置的"业务保留期"（5/30 年按类别）
   - 销毁层：超过保留期 → **不删除**（GSP 7.107 + 5.69）→ 移到深度归档（OLAP/冷存储），仅元信息可查（数据本体可申请恢复）

2. **保留期分类配置**（M1-008 配置中心新增字段类别 `data_retention_policy`）：
   ```yaml
   普通业务数据: 5 年
   特殊药品流通台账: 30 年
   特殊药品销毁记录: 30 年
   追溯码上报记录: 5 年
   冷链温湿度: 5 年
   不合格品销毁: 5 年
   客商资质副本: 资质有效期 + 5 年（计算项）
   主数据: 永久（标记 retention=permanent）
   系统配置变更: 3 年
   ```

3. **自动归档作业**：
   - 每月 1 日凌晨执行（默认值，可配置 `archive_job_cron`）
   - 按表按分区扫描；超过在线层期限的分区批量移到归档层
   - 作业失败 → 自动重试 3 次 → 触发 H4 企微告警仓库主管 + 系统管理员
   - 作业进度 / 历史 / 失败原因可在 PC 端查询

4. **归档查询透明**：业务模块查询不感知数据所在层，由查询层路由；查询涉及归档分区时返回提示（如"包含 18 个月前的数据，预计 N 秒"）

5. **销毁层数据恢复**：
   - GSP 检查需要时，运维管理员可申请恢复某段时间数据（默认 24 小时内可恢复，可配置）
   - 恢复操作必须双人审批（管理员 + 仓库主管）+ 审计记录
   - 恢复后数据进入归档层，访问完成后自动回到销毁层

6. **特殊药品强校验**：麻精毒放销毁记录 / 流通台账（M6-004 / M-SA / M-TC）走独立归档策略 30 年，与普通业务数据分区隔离；特殊药品归档作业失败立即升级到管理员级告警

7. **资质副本计算保留期**：客商资质（M-QL 档案补录、M1-002 供应商、M1-003 客户）保留期 = `MAX(资质失效日期, 关联业务最后一笔交易日期) + 5 年`，由作业按合同状态动态计算

8. **审计的归档**：本归档作业自身写 H2 审计（actor=`system-archive-business`，含归档表名、行数、归档前后位置、操作时间、approval_source=`定时任务`）

9. **配套备份**：归档层数据归 H10 数据库备份覆盖（备份策略与在线层一致）；销毁层数据归 H10 冷备份覆盖（独立介质，离线保存）

10. **业务模块的归档接入要求**：
    - 业务模块新增表时，必须在数据字典声明 `data_retention_policy` 字段（不写则默认"普通业务数据 5 年"）
    - 新增 `data_retention_policy` 类别需走 ADR 决策（合规变更，非配置变更）

### 异常路径

- **归档时该数据正在被查询/写入** → 跳过本次，下一次作业重试；连续 3 次跳过 → 告警
- **归档介质满 / 数据库连接异常** → 作业暂停 + 告警 + 不影响在线业务
- **保留期到达但业务流程未结束**（如审批中的销毁单）→ 推迟到流程关闭后再算保留期
- **多货主切换后数据归属**：原货主数据保留期按原货主合同延续，不因切换重置

## 业务边界声明

> H2 审计模块的边界：
>
> 1. **不主管业务**：本模块只做"记录"，不做"判断"
> 2. **审计字段单一来源**：M3-003 6→7 类审批源 + M6-002 22 操作枚举是唯一标准
> 3. **append-only 不可改变**：本不变量是 GSP 合规底线，不可妥协
> 4. **保留 ≥ 5 年**：与 H10 备份共同保障 GSP 数据完整性
> 5. **多货主隔离**：审计也按货主切片，不暴露跨货主信息
