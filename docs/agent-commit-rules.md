# AI 默认本地提交规则

> 本文定义 AI 在 WMS 仓库中何时可以不再额外询问用户，直接完成本地提交。这里仅放本地提交规则；推送、打 tag、main 分支操作和破坏性 Git 操作仍按 `AGENTS.md` 禁止事项执行。

## 适用范围

满足本文规则时，AI 可以在完成任务后默认执行本地 `git commit`，不再单独询问“是否提交”。

不适用范围：

- 用户明确说“只分析 / 只计划 / 只 review / 不提交 / 先别提交”。
- 推送、打 tag、合并 main、强制推送、删除分支、`git reset --hard`、`git clean -f`。
- 业务、法规、安全、生产数据或架构决策仍有未确认问题。

## 默认提交条件

同时满足以下条件才允许默认本地提交：

1. 本轮任务已经完成，且没有阻断级 review 问题。
2. 变更是单一主题；跨主题时必须拆成多个提交。
3. 只暂存任务相关文件；禁止 `git add .`。
4. 没有暂存 `.env`、私钥、真实令牌、真实密钥、生产数据导出或敏感截图。
5. `git diff --check` 通过。
6. `just gov-t1` 通过。
7. 已按变更范围跑最小相关测试；无法运行时必须说明原因，默认不提交。
8. 生成文件必须由项目命令生成，例如 OpenAPI / api-client 用 `just openapi-sync`。
9. 提交信息符合 [governance.md §3.2](governance.md#32-conventional-commits)，scope 必须使用白名单。
10. 单提交变更 `>= 800` 行必须拆分或说明治理例外；`600-799` 行只需要在最终汇报说明。

## 脏工作区处理规则

脏工作区不等于不能提交。AI 必须先分类，再处理。

1. 先运行 `git status --short --branch` 和 `git diff --stat`。
2. 给每个脏路径归类：
   - `本轮任务`：本轮明确读取、修改和验证的文件。
   - `同主题遗留`：能从当前对话、子代理输出或已有文档明确归属到同一主题的文件。
   - `其他主题`：与本轮目标无关，但可保留在工作区的变更。
   - `未知归属`：无法判断是谁改的、为什么改、是否应保留。
   - `风险文件`：`.env`、密钥、真实 token、生产数据、敏感截图或破坏性 Git 操作产物。
3. 处理方式：
   - `本轮任务`：按默认流程验证、显式暂存、提交。
   - `同主题遗留`：先 review，同一主题可合并提交；跨主题必须拆提交。
   - `其他主题`：不暂存、不回滚；最终汇报说明保留。
   - `未知归属`：不提交，停下说明需要用户确认或后续归类。
   - `风险文件`：不提交，立即停下报告。
4. 只有目标文件本身存在未确认旧改动，或无法用显式路径隔离暂存时，才阻止默认提交。
5. 每次提交前必须看 `git diff --cached --stat`，确认 staged 只包含当前分组。

## 遗留脏区收口流程

当工作区已经存在多组未提交变更时，按以下流程把它们处理掉：

1. 建立脏区清单：记录 `git status --short --branch`、`git diff --stat`、未跟踪路径和当前分支 ahead / behind 状态。
2. 逐路径标注归属：每个路径必须落到 `本轮任务`、`同主题遗留`、`其他主题`、`未知归属` 或 `风险文件`。
3. 先处理能闭环的分组：每组必须有明确主题、明确验证命令和明确提交信息；不能因为工作区很脏就跳过 review 或验证。
4. 混合文件单独处理：同一文件里同时包含多个主题时，只有在能安全、非交互地拆分 staged hunk 时才拆；否则整文件留在对应主题分组，或停下让用户决定。
5. 风险和未知先不动：`风险文件` 立即报告；`未知归属` 不提交、不回滚、不删除，先等待归类。
6. 每个分组闭环后再继续下一组：`git add <明确文件...>`、`git diff --cached --stat`、提交、`git status --short --branch`。
7. 最终汇报必须列出已提交分组、仍保留的其他主题、未知归属和风险文件；不能笼统说“已清理”。

## 禁止默认提交

出现任一情况时，不允许默认提交，必须停下说明：

- 本轮目标文件有无法区分归属的旧改动，或暂存区无法隔离当前分组。
- 目标文件已有用户改动且本轮变更会覆盖或重排它。
- 有失败测试、失败治理脚本或未解释的生成物。
- 需要新增模块、故事、字段、状态、角色、审批源或跨模块语义。
- commit-msg / pre-commit hook 拒绝提交。
- 需要用户决定提交拆分方式。

## 分组提交规则

- 文档、治理脚本、后端、前端、测试、运行配置优先分开提交。
- 同一功能的接口、DTO、OpenAPI、api-client 和最小测试可以放在一个提交。
- 纯格式化不得和功能混在一起。
- Breaking Change 单独提交，并在脚注写 `破坏性变更：<说明>`。

## 默认流程

1. `git status --short --branch`
2. `git diff --stat`
3. review → 修复 → 再 review
4. 运行 `git diff --check`、`just gov-t1` 和相关测试
5. `git add <明确文件...>`
6. `git diff --cached --stat`
7. `git commit`
8. `git status --short`

## 规则迭代

每次默认提交失败或需要用户临时裁决时，先判断是否是可复用规则缺口。

- 如果是一次性业务判断，只记录在最终汇报。
- 如果会复发，更新本文或对应 skill / runbook。
- 更新本文后至少运行 `git diff --check` 和 `just gov-t1`。
