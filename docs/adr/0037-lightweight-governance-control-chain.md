# ADR-0037：轻量治理控制链（G1-G4）

- 状态：Accepted
- 决策日期：2026-07-14
- 决策人：项目主人
- 起草人：AI 助手
- 关联：ADR-0003 / ADR-0006 / ADR-0016 / ADR-0035 / `docs/governance.md` / `governance/gate-rules.toml`

---

## 背景

ADR-0003 已确定 5 类治理对象、T1-T4 执行 Tier、Baseline 和 diff 触发；ADR-0006
另定义 L1-L11 测试维度。项目进入 Wave 6 后，治理资产已扩展到文档、代码、质量、
流程、运行证据和外部依赖，但出现了三个问题：

1. “治理类别、文档层、测试层、执行 Tier”都使用分层术语，规则从决策到证据的链路不直观。
2. 规则、触发、调度和证据分散在文档、TOML、Python 和 justfile，容易多头维护。
3. T1 实测超过 10 秒预算；继续无差别增加脚本会降低治理采纳率。

治理必须覆盖医药 WMS 的法规、审计、权限、数据一致性和真实运行证据，同时不能把普通
开发变更拖入重型审批或全量发布验证。

## 候选方案

### A. 新建集中式治理平台

把规则、审批、豁免、证据和仪表盘全部迁入独立服务。

- 优点：集中展示，扩展空间大。
- 缺点：引入新平台、数据库和运维面；当前没有足够使用证据支撑成本。

### B. 在现有治理资产上增加轻量 G1-G4 控制链

G1-G4 只定义规则从决策到证据的责任边界；复用现有 ADR、治理文档、
`gate-rules.toml`、治理脚本、justfile、Git Hook、Gitea CI 和证据 JSON。

- 优点：不引入新依赖或服务；可以渐进整理现有治理；机器可追溯。
- 缺点：需要维护现有配置和脚本的一致性。

### C. 只补一份说明文档

- 优点：改动最小。
- 缺点：无法阻止配置、调度和文档继续漂移。

## 决策

采用方案 B：在 ADR-0003 之上增加轻量 G1-G4 控制链，不取代现有 5 类、T1-T4、
L1-L11 和文档 L1-L4。

### G1 决策层

记录“为什么必须治理”。复用法规条款、客户合同、已确认业务/合规决策、ADR 和治理规范，
不新增统一决策编号。

冲突时按以下顺序处理：

```text
适用法规/监管要求
> 客户合同
> 人工确认的合规与业务决策
> ADR 与工程规范
> 代码实现
```

法规是否适用由业务或合规人员确认，AI 不作最终裁定。文档 L1-L4 表示稳定性和变更流程，
不能解释为技术 ADR 可以覆盖适用法规。

### G2 规则层

把 G1 决策转成可重复判断的规则。规则 verdict 只有 `pass` 和 `fail`；warning/info 属于
非阻塞报告，不冒充门禁。每条可执行规则必须能追溯到决策来源，并具有稳定 `rule_id`。

当前实现复用 `governance/gate-rules.toml`：未显式登记 `rule_ids` 时，从现有检查名生成兼容
ID；脚本合并、重命名、需要 Waiver 或需要独立证据时必须显式保留原 `rule_id`。一个脚本
可以检查多条规则，一条规则也可以由多个检查共同证明。

存量且未触碰的规则可继续使用兼容 ID 和默认来源；新增规则，以及红线、真实运行证据、
Tier/context 调整或脚本重命名涉及的规则必须显式登记 `rule_ids` 与 `source`。这是一条
按风险迁移规则，不要求一次性复制全部存量元数据。

### G3 门禁层

负责“何时、在哪里、由什么执行”。Tier 表示成本预算，context 表示执行场景，两者正交：

| Tier | 预算 | 执行 context | 用途 |
|---|---:|---|---|
| T1 | `<10s` | local / pr / main / release / runtime | 全量快速红线 |
| T2 | `<120s` | local / pr / main / release / runtime | 任务结束与 diff 检查 |
| T3 | `<5min` | pr / main / release / runtime | 风险或路径命中的集成门禁 |
| T4 | `<30min` | main / release / runtime | 定时、预发布和完整验证 |

高 Tier 入口累积低 Tier 门禁，因此 main/release/runtime 不能过滤掉 T1-T3。PR 必跑 T1/T2，
按 diff 追加 T3；T4 不在每个 PR 全量运行。Gitea CI 只编排现有命令，不复制业务规则。

### G4 证据层

保存规则执行结果和真实运行证明。小型 JSON、摘要和哈希可入库；大日志、工单、截图原图和
硬件录像保存在外部证据库，仓库只保存不可变引用。ADR-0035 的真实 dev/staging、外部系统
和硬件要求不变；缺少外部条件时状态是 `blocked`，不能记为 `pass`。

规则 verdict 与门禁运行状态分离：

- 规则 verdict：`pass` / `fail`。
- 执行状态：`passed` / `failed` / `error` / `blocked`。
- `error` 和 `blocked` 永远不能关闭 gate。

工作流文件和本地契约测试只能证明 CI 配置就绪；首次真实 Gitea 运行 URL 才能作为远端
G4 证据。提交和推送发生前，该证据保持 `blocked`，不得用本地结果代替。

## 后果

- 正面：
  - 决策、规则、门禁和证据形成可追溯控制链。
  - 复用现有资产，不增加治理平台或运行依赖。
  - Tier 与执行场景解耦，普通 PR 不被真实硬件和外部系统阻塞。
- 负面：
  - `gate-rules.toml` 和调度器需要承载少量元数据。
  - 现有 warning-only 检查和重复脚本需要渐进整理。
- 风险：
  - 元数据过多会形成新负担；因此只保留 rule/source/context 等最小字段。
  - 自动生成 rule_id 仍与旧检查名有关；脚本重构时必须显式冻结 ID。

## 实施约束

1. G1-G4 是逻辑分层，不创建四套目录、服务、数据库或审批系统。
2. 新阻塞规则只允许来自红线风险、真实事故/漏检，或同类问题出现至少 3 次。
3. T1/T2 时间预算是硬约束；超时先重分 Tier、合并重复扫描，再考虑增加资源。
4. 相同输入或同领域的检查优先合并；没有独立检测价值的脚本应退役，不追求固定脚本数量。
5. Baseline 只承接已有非红线技术债，必须单调下降；关键不变量禁止 Baseline。
6. 临时 Waiver 必须有人工作出的批准引用、理由和到期时间；首次真实需要前不建设独立存储。
7. 外部依赖等待单独记为 `blocked`，不得塞入 Baseline 或 Waiver。
8. AI 可以盘点、运行检查和修复无业务语义问题；G1 决策、Waiver、GSP/安全结论和发布签署由人确认。
9. Gitea PR 运行 T1/T2 和 diff 触发的 T3；main 运行 preflight；完整 T4 由人工预发布入口触发。
10. 新规则和调度变更必须有最小可运行测试，并通过 T1。
