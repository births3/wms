# AI 协作规范

> 本文档承接根 `AGENTS.md` 不再展开的长规范。根文件只保留入口约束；这里记录确认流程、风险判断、版本控制协作、审查方式和治理优先级。

## 1. 文件放置规则

| 位置 | 内容 |
|---|---|
| `AGENTS.md` | 项目原则、常用命令、验证要求、协作约定、禁止事项 |
| `*/AGENTS.override.md` | 模块独有规则 |
| `.agents/skills/<skill>/SKILL.md` | 复杂流程 |
| `.codex/config.toml` | 本机 Codex 模型、沙箱、MCP、钩子、审批默认值 |
| `.codex/rules/*.rules` | 本机命令允许 / 提示 / 禁止规则 |
| `docs/*.md` | 详细说明、经验手册、长规范、背景材料 |

当前仓库 `.gitignore` 明确 `.codex/` 是本机配置，不作为项目资产提交。

## 2. 需求确认格式

AI 向用户提出需要确认的问题时，使用下列表格：

```markdown
| # | 问题 | 选项/说明 | 建议 |
|---|------|---------|------|
| 1 | 简短问题描述 | A) 选项一 B) 选项二 C) 选项三 | 建议选 A |
```

规则：

- 每个问题必须有编号。
- 有明确选项时列 A/B/C。
- 无明确选项时给建议默认值，用户可直接回复“可以”。
- 一次问题不超过 10 个。
- 按紧急程度排序：必须现在决定、需要确认、可用默认值。

用户可用 `1A 2B`、`3-6 统一用建议`、`7 详细探讨` 等形式回复。

## 3. 发现缺口时的确认流程

触发条件：

- 功能缺口：业务场景没有用户故事覆盖。
- 模块缺失：需要新增独立业务模块或基础设施模块。
- 设计冲突：已有故事或决策矛盾。
- 抽象机会：多个模块出现重复模式，可抽成公共能力。
- 技术决策：新增依赖、改变数据模型、改变状态机等架构影响。
- 范围变化：故事实现复杂度远超预期，需要拆分或简化。

流程：

1. 描述发现。
2. 分析影响。
3. 给 2-3 个解决方案。
4. 等用户确认。
5. 决策落到 `docs/domain/clarifications.md` 或对应 ADR / runbook。

不需要确认的情况：修复脚本错误、术语违规、文件命名、链接错误、审计追踪补充、代码重构且不改变功能。

## 4. 风险分级

无风险任务可自主修复，需同时满足：

- 不改变业务语义。
- 不引入新概念、新字段、新状态、新角色、新模块。
- 不影响数据模型。
- 可被治理脚本验证。
- 单主题可回滚。

有风险任务必须确认，满足任一即有风险：

- 业务规则取舍。
- GSP 合规边界。
- 新增规范字段。
- 新增、移除、拆分故事。
- 改角色、状态机、字段约束、审批源、触发源。
- 跨模块语义变化。
- 引入无既存依据的新默认值。
- 可能误删用户内容或生产数据。

边界模糊时默认有风险。

## 5. 版本控制协作

红线：

- 不主动提交、推送、打标签。
- 不强制推送、不硬重置、不清理工作区、不删除分支。
- 不修改 git 全局配置、钩子、远程配置。
- 不提交可疑文件：`.env`、私钥、真实令牌、真实密钥。
- 跨主题工作区不使用 `git add .`。

默认本地提交按 [agent-commit-rules.md](agent-commit-rules.md) 执行；满足条件时不再额外询问用户是否提交。

提交时：

1. `git status --short`。
2. `git diff --stat`。
3. 跨主题或 `>= 800` 行先拆分。
4. 单主题 `600-799` 行提示接近上限。
5. 起草符合 [docs/governance.md §3.2](governance.md#32-conventional-commits) 的提交信息。
6. 满足默认提交规则则直接提交；不满足时说明阻塞。
7. 报告 lefthook pre-commit / commit-msg 结果。

用户要求推送时：先确认目标分支；main 分支必须显式确认；推送前建议 T3 预检。

## 6. AI 产出审查

每次重要产出后自查：

- 数字有出处。
- 决策有候选方案。
- GSP 引用具体到条款。
- 风险有应对。
- 修改可回滚。
- 推断和未验证内容明确标注。
- 不冒充法规、业务、安全最终权威。
- 跨文档一致。
- 不把脚本可检的问题留给人工审查。

反模式：数字虚高、过度抽象、照搬不思考、概念漂移、忽略治理脚本、未读先答、跨主题混提交。

## 7. 修复和审计优先级

优先级：

| 级别 | 对象 | 验证 |
|---|---|---|
| P0 | 现有脚本可检查的违规 | `just gov-t1` |
| P1 | 可脚本化但当前未覆盖的问题 | 先加脚本再修 |
| P2 | 必须人工语义判断的问题 | 记录评审报告 |

同类问题在 3 个以上文件出现，优先脚本化。脚本误报先修脚本，不用批量文档噪音掩盖。

## 8. 设计流程

标准顺序：

1. 用户故事。
2. 概念审计。
3. 模式提炼。
4. 领域模型 / API 草案。
5. 外向内 TDD 开发生产前端纵向切片。
6. 使用开发 Mock 在生产前端完成业务走查。
7. 领域模型 / API 契约、权限、审计和幂等要求冻结。
8. 接入真实后端并用真实数据 E2E 收口。

概念审计使用用户、开发者、运维、安全、数据、时间、失败、边界 8 个视角。模式提炼优先看词频、依赖、用户不可见能力、技术关注点分离。

## 9. Loop Engineering 闭环

需要多轮执行、检查、反馈的任务，按 [agent-loop-engineering.md](agent-loop-engineering.md) 跑最小闭环：先定义目标、输入、检查、反馈和停止条件，再小步修改和验证。

执行入口：

- 长说明和模板：`docs/agent-loop-engineering.md`
- 操作技能：`.agents/skills/wms-loop-engineering/SKILL.md`

## 9. 界面术语消歧与全链路排查约定

在处理用户针对前端界面（如“字段栏透明”、“筛选错位”、“按钮没反应”）的反馈时：

1. **禁止代码符号先入为主**：不得仅凭代码变量名（如 `*Field*`）做孤立假设，必须区分用户视觉视角与开发者代码视角（例如“字段栏”指表格 `TableHeader`，“字段设置”指弹窗面板）。
2. **全链路穷举排查**：凡涉及 UI 定位问题，必须同时审查【底层原语（如 `ui/table`）】、【业务容器（如 `DataTable` / `DataGrid`）】与【弹窗浮层（`Popover` / `Dialog`）】。
3. **动态场景审视**：重点验证纵向滚动、表头吸顶（`sticky top-0`）、悬停 hover 与冻结列交汇等动态交互场景，防止仅静态看单行代码遗漏 alpha 半透明透光。
4. **硬测试固化**：发现视觉/样式盲区后，必须将实体背景或结构规则补充为可自动运行的测试断言（如 `table-row-background.test.ts`）。
