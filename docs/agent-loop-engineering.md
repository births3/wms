# AI Loop Engineering 落地规范

> 本文档把 Loop Engineering 转成 WMS 仓库可执行的 AI 协作闭环。复杂执行步骤见 `.agents/skills/wms-loop-engineering/SKILL.md`。

## 1. 来源和定位

参考文章：[金尘马《小白教程：一文带你搞明白 Loop Engineering 并快速上手》](https://x.com/i/article/2070176606140911617)，发布于 2026-06-26。

在本仓库里，Loop Engineering 不是新治理体系，也不替代 TDD、ADR、用户故事和门禁。它只规定 AI 如何把一次任务跑成可检查、可反馈、可停止的小闭环。

一句话定义：

> 给 AI 设计一套围绕目标反复执行、检查、修正和停止的工作循环，而不是让人每一步都亲自提示。

## 2. 什么时候用

适合使用：

- 任务会重复发生，例如文档治理、故事审查、原型矩阵维护、测试修复。
- 结果能检查，例如链接、索引、脚本退出码、故事字段、视觉基线、人工验收清单。
- 失败能反馈，例如缺索引就补索引，脚本失败就修失败项，业务不确定就停止确认。

不适合使用：

- 标准模糊的纯创意任务。
- 没有事实来源的判断。
- 需要业务、法规、安全最终拍板的事项。
- 高权限操作，例如生产数据、账号、支付、删除、发布。

## 3. 最小闭环

| 环节 | WMS 默认要求 |
|---|---|
| 目标 | 写成可验收结果，不写成愿望。 |
| 输入 | 列出可依据的文档、代码、脚本、用户确认。 |
| 执行 | 一次只做一个小主题，保持 diff 小。 |
| 检查 | 先脚本，后人工语义自查。 |
| 反馈 | 只修失败项，不顺手扩范围。 |
| 记录 | 最终报告改了什么、验证结果、剩余风险。 |
| 停止 | 通过检查、遇到必须确认事项、连续同类失败或超出范围时停止。 |

## 5. WMS 检查清单

每次按 Loop 执行时至少检查：

- 文档使用中文。
- 文件位置符合 `AGENTS.md` 文件分工。
- 新增长规范进入 `docs/`，复杂流程进入 `.agents/skills/`。
- 没有引入未经确认的新模块、故事、字段、状态、角色或业务默认值。
- 脏工作区中只触碰本轮相关文件。
- 前端页面或 API client 变更时，除了静态脚本，还要检查运行时数据入口：真实后端路由或 `apps/web-admin/vite.config.ts` dev mock 路由至少一边可达；开发 mock 模式下用相关 self-check 或 `curl 9002` 覆盖页面调用的 API，防止 `Dev mock route not found`。
- 涉及用户故事、菜单页、模块验收、补齐缺失功能或质量矩阵时，先跑 `python3 scripts/governance/check_scope_gap_discovery.py --json`；“全部/闭环/补齐/验收”类任务按模块追加 `--strict --module <模块>`。
- 可脚本验证的问题优先跑脚本，至少执行 `git diff --check` 和 `just gov-t1`。
- 最终报告包含验证退出码和未解决风险。

## 6. 常见跑偏

- 把长提示词当 Loop：没有检查、反馈和停止条件，就不是闭环。
- 目标太大：一次做整个系统，失败后不知道修哪里。
- 标准太虚：例如“更好一点”“更深入一点”，无法验收。
- 没有人验收：AI 自己做、自己批改、自己宣布完成。
- 硬连概念：找不到关联时允许标记“未关联”，不要强行制造关系。
- 权限过大：第一次跑低风险任务，不给删除、提交、发布、生产操作权限。
