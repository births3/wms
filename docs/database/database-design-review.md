# 数据库设计审查矩阵

> 基于 `docs/database/table-catalog.md` 和 `backend/migrations/*.sql` 的人工审查。本文不替代 migration，也不自动判定业务正确性。

## 1. 总体结论

当前 52 张表的模块边界基本清楚，能支撑 Wave 1 到 Wave 5 的审计、鉴权、主数据、入库、库存、出库、冷链、计费、包装站、TMS 和系统字典第一批能力。作为渐进式 WMS 后端模型是合理的；作为大型 WMS 正式版，还需要继续推进状态字典化、完整主数据业务接口和 M2 多次到货模型确认。

## 2. 模块矩阵

| 范围 | 表数量 | 结论 | 主要风险 |
|---|---:|---|---|
| H2 审计 | 3 | 合理 | `audit_event` 无 `created_at` 是 ADR-0025 特例，不按通用业务表处理 |
| H1 鉴权 | 7 | 基本合理 | 用户、角色、权限是全局 + owner 绑定混合模型，需继续靠 service 防止跨货主授权 |
| M1 主数据 | 7 | 基本合理 | 已补商品、供应商、客户、地址、仓库、库区、库位基础表；业务 API 与审计写路径仍需后续实现 |
| M1 系统字典 | 2 | 合理 | 已支持全局与货主覆盖，但状态类字段尚未系统性接入 |
| M2 入库 | 6 | 当前切片合理 | 一单一次收货闭环；若支持多次到货、多批号拒收，需要新模型确认 |
| M3 库存 | 3 | 合理 | `inventory_batches` 聚合余额 + movement 流水方向正确 |
| M5 冷链 | 3 | 合理 | 当前只接收外部判定，不负责采集和阈值判定 |
| M4 出库 / 追溯 | 7 | 基本合理 | 追溯事件表用复合主键，和通用 `id UUID` 规则不同，需要保留为事件表例外 |
| M-PK / M8 / M9 / M10 | 10 | 可用 | 计费周期字段已改为 `DATE`，对外 DTO 仍保持字符串 |

## 3. 规则矩阵

| 维度 | 当前状态 | 判断 | 建议 |
|---|---|---|---|
| 表命名 | 基本都是 `snake_case` 复数或集合名 | 通过 | 新表按 `database-design-standards.md` |
| 索引命名 | 采用 `<table>_<purpose>_idx` | 通过 | 文档已收口为当前风格 |
| 货主隔离 | 45 张表直接有 `owner_id`，1 张分区继承 | 基本通过 | 继续保留 `check_owner_scope_sql.py` |
| 跨货主 FK | 关键父子表已补 `owner_id + id` 复合 FK | 基本通过 | `container_recoveries.dispatch_id` 因 nullable + `ON DELETE SET NULL` 暂保留 service 校验 |
| 主数据依赖 | 已补 M1 PostgreSQL 主数据表 | 基本通过 | 后续补业务 API、审计写入和导入导出 |
| 状态字段 | 大量 `status TEXT` | 可接受但有风险 | 可配置/可运营状态接入系统字典或状态机规范 |
| 审计 | append-only、分区、封档表已落 | 通过 | 继续按 ADR-0025 |
| 幂等 | `idempotency_request` 已有 | 通过 | 新写接口继续复用 |
| migration DML | 系统字典 migration 写预置项 | 可接受 | 仅允许确定性系统种子数据 |

## 4. 优先级

| 优先级 | 项目 | 原因 |
|---|---|---|
| P0 | 保持 `just gov-t1` 和 owner SQL 检查通过 | 已有脚本可验证 |
| P1 | 状态 / 单据类型 / 参数类字段接入系统字典规则 | 避免自由文本状态扩散 |
| P1 | 补 M1 主数据业务 API 与审计写路径 | 表已存在，业务入口仍需按故事实现 |
| P2 | M2 多次到货、多批号拒收是否纳入当前模型 | 需要业务确认，不能靠数据库审查拍板 |
