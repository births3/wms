# WMS PlantUML 文档

## 先读

- `AGENTS.md`
- 当前任务相关的用户故事、ADR、RTM、数据库文档、OpenAPI 或代码。
- 若是业务流程图，先确认流程状态、审批源、审计、货主覆盖和历史解释规则。

## 产物规则

- 图文件使用 `.puml`，每个文件只表达一个主题。
- 复杂主题使用目录承载：
  - `docs/diagrams/<topic>/<name>.puml`
  - `docs/diagrams/<topic>/docu.md`
- `docu.md` 是图的中文说明，不是新事实源；事实仍以用户故事、ADR、RTM、OpenAPI、数据库文档为准。
- `docu.md` 至少包含：目的、适用范围、关联文档、如何读图、关键约束、维护规则。
- 所有说明用中文；PlantUML participant / entity 名称可中英混合，代码对象名保留英文。

## 图类型选择

- 调用链、接口交互、事务边界：用时序图。
- 业务步骤、分支、审批、异常处理：用活动图。
- 模块边界、依赖方向、平台能力：用组件图。
- 表关系、主外键、唯一约束：用实体关系图。
- 状态流转：用状态图。

## WMS 约束

- 不把图画成单页面功能；跨 M1/M2/M3/M4/H2/M-CG/M-PM 的能力必须体现模块边界。
- 涉及单据类型时，标明 `document_type` 来源于 M1 系统字典。
- 涉及单据号时，标明 M-CG 统一生成，业务模块不得自行拼号。
- 涉及“作业前 / 确认后 / 发货时 / 同一事务”等时序约束时，图中节点顺序必须与事实源一致。
- `docu.md` 写到的横向能力、合规约束和关键节点，必须在相关 `.puml` 中出现；不适用时在 `docu.md` 明确说明范围外。
- 涉及 GSP、批号、效期、温控、特殊药品、双人操作、审计时，图和 `docu.md` 都必须显式标注约束。
- 涉及数据库写入时，标明事务边界、幂等键、审计写入和 no-gap / standard 策略。
- 涉及 no-gap 单据号时，发号、计数器递增、生成记录和业务单据写入必须画在同一数据库事务内；禁止画成 M-CG 单独提交后业务模块再写单据。

## 检查清单

1. `.puml` 必须有 `@startuml` 和 `@enduml`。
2. 图中不得出现未确认的新模块、字段、状态、角色或审批源。
3. 图中不得包含真实密钥、生产地址、真实客户数据。
4. `docu.md` 必须链接到已有事实源，不能只写口头结论。
5. 活动图和状态图必须按事实源逐节点核对前置 / 后置顺序，例如 M-VR 查询必须在对应作业前，库存扣减必须在发货确认后。
6. 修改后运行 `git diff --check`；如改到治理文档，运行 `just gov-t1`。

## 自我 review

每次生成或修改图文后，先自查再汇报：

1. 路由正确：任务属于 PlantUML 图文沉淀，不该改故事、ADR、RTM、OpenAPI 或代码。
2. 事实可追溯：`docu.md` 链接事实源；图中关键模块、字段、状态、审批和约束都有来源或标为待确认。
3. 顺序一致：对照事实源核对每个“前 / 后 / 时 / 同一事务”节点，避免把策略查询、审批、扣减、审计画到错误位置。
4. 图文一致：参与方、表名、状态、事务边界和说明一致；`docu.md` 的关键约束不能只停留在文字里。
5. no-gap 一致：单据号图中不能出现发号事务先提交、业务单据后写入的断链。
6. WMS 定位正确：横向能力不画成单页面功能；单据类型、单据号、GSP、批号、效期、温控、双人操作、审计约束已标出。
7. 治理明确：报告链接、mkdocs 导航、空白检查和 T1 结果。

## 自我迭代

发现重复错误、漏检查、表述不清或触发边界不准时，小步迭代本技能：

- 只改 `.agents/skills/wms-plantuml-docs/` 下的必要文件，除非入口说明也必须同步到 `AGENTS.md`。
- 优先补规则或检查清单，不新增脚本；只有同类错误出现 3 次以上，才考虑脚本化。
- 迭代后运行 yao 三项检查、`git diff --check` 和 `just gov-t1`。
- 如果新增能力超过“PlantUML 图文沉淀”，停止并建议拆成新技能。
